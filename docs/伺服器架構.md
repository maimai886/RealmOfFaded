# Realm of Faded 伺服器架構與防串改規格

2026-09-15 訂。依使用者要求「以多人 MMORPG 心態開發、本機架伺服器測試、防止資料被串改」。
參考：`docs/歷史/參考規格.md` 第 4 節（rAthena 權威模型、Gambetta 延遲補償、godot-tiny-mmo 分層）。

## 0. Rust 版現況

2026-09-28 M1 做完伺服器這半邊。第 2 節以後寫的是舊專案 GDScript 伺服器，行為照搬，檔名和程式位置以這一節為準。

- 伺服器在 `rust/crates/server`，`cargo run -p rof-server -- --port=7780`；伺服器列表設定在 `rust/crates/server/config/servers.json`；M1 的資料庫在記憶體，關掉伺服器帳號角色就沒了
- 客戶端版本 `rof_protocol::CLIENT_VERSION` 現在是 `0.1.0`，動到協定就改
- M1 的指令：`auth.login`、`server.list`、`char.list`、`char.create`、`char.enter`、`move.to`、`move.stop`、`ping`；推送：`world.enter`、`world.blockers`、`entity.spawn`、`entity.despawn`、`entity.state`、`self.stats`、`heartbeat`、`kick`。欄位和型別在 `rust/crates/protocol/src/message.rs`
- 碰撞、尋路、點地移動在 `rof-core`，客戶端預測、內插、時鐘在 `rof-netcore`，伺服器和客戶端跑同一份

和舊專案不一樣的地方：

- **移動指令從伺服器收到之後的下一個 tick 邊界開始走**。第 k 個 tick 涵蓋地圖時間 (k−1)×50 到 k×50 毫秒，`entity.state` 的時間是 k×50。客戶端的套用時間是「伺服器現在加來回時間，往上取到 50 毫秒」再換回本機時間。舊公式是加單程減 5 毫秒，會比伺服器晚一個 tick，每次起步被拉 0.175 公尺
- **`ping` 回應和 `world.enter` 的 `time_ms` 是送出那一刻的地圖時間**，客戶端拿來對時鐘，進地圖後先 ping 幾次再走；舊的 `world.enter` 取到 tick，最多差 50 毫秒，第一步就會算錯 tick
- **點地移動站上終點或被擋住才停**。舊的離終點 0.1 公尺就停，伺服器一個 tick 判一次、客戶端一幀判一次，兩邊停的點不一樣
- 解析前掃到超長數字，或解析時碰到 NaN、Infinity、1e400 這種 f64 放不下的數字，一律 `bad_json` 踢線；1e300 這種放得下的回 `out_of_range`
- 保留名字在 `data/reserved_names.json`，`sproutia` 換成 `rof`、`realmoffaded`
- 安全稽核限流照「同一種事件、同一個來源」每分鐘 10 筆，全部合計 300 筆
- 角色摘要 M1 沒有 HP、SP、能力值，M2 有數值公式再補
- 伺服器送出關閉訊號後等客戶端回應才斷線，最多 1 秒；太早斷的話客戶端再送東西會收到 RST，作業系統把還沒讀的 `kick` 丟掉
- 實測拉回，`rust/crates/server/tests/play.rs`：本機伺服器、點樹後面繞過去，預測和伺服器最大誤差 0.018 到 0.022 公尺，平滑拉回 0 次，跑 10 次都一樣；Windows 的 tick 計時器會晚 0 到 15 毫秒

## 1. 總原則
1. **伺服器是唯一權威**：位置、HP/SP、經驗、屬性點、技能、道具、裝備、金錢、地圖，全部只在伺服器改。
2. **客戶端只送意圖**：例如「走到這裡」「攻擊 12 號」「使用紅色藥水」。伺服器驗證通過才執行，再把結果送回。
3. **客戶端顯示只根據伺服器送來的狀態和事件**；自己的移動可以先預測，但以伺服器為準。
4. **客戶端安裝包不含伺服器程式與密鑰**：`server/` 目錄在客戶端匯出時排除。
5. **所有邏輯時間用伺服器時鐘**：客戶端送來的時間戳一律不採信。

- **傳輸層**：WebSocket，走 TCP。原因是 RO 也用 TCP，手機、網頁都能跑，之後可以直接升級成 wss 加密。Godot 用 `TCPServer` 加 `WebSocketPeer`。
- **綁定位址**：`--bind=` 預設 `127.0.0.1` 只有本機連得到，可以給 IPv4、IPv6 位址或 `*` 代表所有網路介面，主機名稱不收，`localhost` 換成 `127.0.0.1`。
  伺服器本身只講 ws 不做 TLS，綁 `127.0.0.0/8`、`::1` 以外的位址時啟動會印警告：對外一定要在前面擺做 TLS 終結的反向代理讓玩家走 wss，
  防火牆只開代理的 port。雲端的做法是伺服器維持綁 `127.0.0.1`，同一台機器的代理連進來；代理在別台機器時才綁內網位址。
  解析在 `ws_server.gd parse_bind_address`，測試在 `tests/test_server_bind.gd`
- **開發測試**：客戶端啟動時如果連不到 `ws://127.0.0.1:7777`，而且目前是開發版，就自動用 `OS.create_process` 在本機啟動一個 headless 伺服器。
  命令列帶了 `--server=` 或任何 `--dev-` 參數時一律不開，規則和這個功能還要不要留見第 10 節啟動。
- **登入名額設定**：`--login-slots=N` 全服同時算密碼雜湊的名額，1～64，預設 CPU 核心數減 1、至少 2；
  `--login-slots-per-source=N` 每個來源的名額，1～全服名額，預設 2；`--ipv6-prefix=N` IPv6 照多長的前綴算同一個來源，32～128，預設 64。
  不合法的值整台不啟動，啟動訊息會印出實際用的三個數字。規則見第 5 節密碼雜湊和「換連線繞限流」

## 3. 封包格式
- 目前用 JSON 文字訊息，方便除錯；`protocol.gd` 包一層，之後可以換二進位。
- 信封格式：`{"v": 1, "t": "類型", "id": 請求編號, "d": {資料}}`
  - `id` 由客戶端遞增，伺服器回應帶同一個 `id`
  - 伺服器主動推送的訊息 `id` 為 0
- 回應格式：`{"t": "resp", "id": n, "d": {"ok": bool, "reason": "", ...}}`
- `reason` 一律是代碼不是句子，句子由客戶端照 `locale/zh_TW.json` 組，規矩在 `docs/多國語系規劃.md`；
  要代進句子的數字或名稱放在同一個回應的 `params`，只放代號和數字，名稱由客戶端自己查資料
- 單一訊息最大 8 KB，超過直接斷線。

### 3.0 交易押住

2026-09-27 加，照 rAthena `src/map/trade.cpp`：`trade_tradeadditem` 擺上去時只記格子和數量，東西在
`trade_tradecommit` 那一刻才離開背包，`trade_tradecancel` 只把畫面上的數量還回去；交易中 `pc.cpp` 的
`pc_dropitem`、`clif.cpp` 的商店和倉庫入口看 `state.trading` 一律拒絕。本作做成押住：

- 擺上去的道具數量和指名的裝備記在背包的押住表 `Inventory.reserve`、`reserve_instance`，金幣記在
  `CharacterData.gold_reserved`；押住只在記憶體，不存檔，所以存檔永遠是完整的背包，當機和斷線不會有東西卡在半路
- 背包的 `count`、`remove`、`instance`、`remove_instance`、`set_instance_mods`、`total_count` 只看得到沒被押住的部分，
  `add_gold` 扣錢時不能扣到押住的金額；所有扣道具和花錢的路徑不用各自檢查就一起擋住，回原本的 not_in_inventory、not_enough_gold
- 交易結束時不管原因都在 `TradeService._end` 全數放開，用交易開始時留下的線上物件放，斷線那一邊也放得開；成交時先放開再換
- `self.inventory` 推給客戶端的 items 是 `Inventory.available_entries`，扣掉押住的；客戶端 `net_session.offer_trade_item`
  的 count 是從背包再擺幾個，送出前加回已擺的數量，因為協定的 count 是總數
- 押住擋掉一般路徑之後，確認和成交的當下還是會重新比對實際數量和押住，繞過押住直接改背包的情況照樣換不成
- 成交時任一邊背包格子、疊放上限、負重或金幣上限放不下就整筆不做，交易不取消，押住維持，兩邊確認清掉

### 3.1 伺服器列表
- 列表只來自伺服器設定檔 `server/config/servers.json`，一台伺服器一筆 `{id, name, capacity, maintenance}`，沒有假資料
- 設定檔讀進來會先檢查：id 只能小寫英數底線、名稱長度 ≤ 16 且不含控制字元、capacity 1～100000、id 不重複、最多 16 台
- `server.list` 回應 `{ok, servers}`，每一筆是
  `{id, name, online, capacity, status, characters}`
  - `online` 是遊戲伺服器當下在這台伺服器上的角色數，`game_server.online_count_on`
  - `status` 由真實人數算出來：`maintenance` 維護中、`full` 人數到上限、`busy` 在線比例 ≥ 0.6、`smooth` 其他；容量 0 是 `offline`
  - `characters` 是這個帳號在該伺服器的角色數，還沒登入時是 0
- 規則和欄位檢查寫在 `src/net/server_list.gd`，伺服器組資料和客戶端檢查回應用同一份；客戶端會把欄位不合的整筆丟掉
- 延遲不在回應裡，由客戶端自己量 `server.list` 或 `ping` 的來回時間
- 人數滿了或維護中時，`char.list`、`char.create`、`char.enter` 都會拒絕，reason 是 `server_full` 或 `server_maintenance`
- `src/net/mock_backend.gd` 用同一套規則，`SERVERS` 常數也只有本機這一台；測試要多台時改 `server_config`

### 3.2 開發指令 dev.command
只有伺服器加了 `--dev-commands` 才存在的訊息類型，用法和指令表在 `docs/開發指令.md`。

## 4. 伺服器模擬
- **固定 tick**：每張地圖 20 Hz，每 tick 50 ms，時間用整數毫秒。
- **移動在 BattleWorld 裡算**
  - 玩家和怪物都有 `move_target` 或 `move_dir`，每 tick 依移動速度前進
  - 指令：`command_move_to`、`command_move_dir`、`command_move_stop`，都回傳是否接受；move_to 目標超出 `set_bounds` 範圍時拒絕，移動結果夾在範圍內
  - 鎖定攻擊時目標在距離外，模擬自己把攻擊者往目標移動；`need_approach` 事件保留，但只是通知。被牆擋住時尋路繞過去，規則在下面「追擊、回家、鎖定走近」
- **點地移動會尋路**，2026-09-27 加，程式在 `src/core/path_finder.gd`，數字在 `data/balance.json` 的 `pathfinding` 區
  - 客戶端只送目的地。伺服器在真的開始走的那個 tick 從自己的位置算路，客戶端預測在套用指令的那一刻用同一份程式、同一份不可行走區算，兩邊走的是同一條路；同一個 tick 連送幾則只算最後一則
  - 規則參考 rAthena `src/map/path.cpp` 的 `path_search`，只引用規則：八方向 A*，直走一格成本 10、斜走 14，和 `path.hpp` 的 `MOVE_COST`、`MOVE_DIAGONAL_COST` 一樣；斜走時旁邊兩格都要能走，不切牆角。
    rAthena 的估計值用曼哈頓距離，會高估，為的是和 RO 客戶端走一樣的鋸齒路；這裡兩邊是同一份程式，改用不會高估的八方向距離
  - 一格 0.5 公尺，是 RO 一格用走路速度換算的大小。一格只有整格都沒碰到不可行走區才算能走，所以格子中心之間的直線一定不撞牆；起點和終點所在的格子例外
  - 直線走得到就直接走直線，不跑 A*，不管多遠；要繞路時把格子路線只留轉彎點，再往後看得到就跳過中間的點，走出來是折線不是鋸齒
  - 目的地在牆裡：先推到最近站得住的地方，和原本一樣；圍起來走不進去：走到附近 32 格內走得到、離目的地最近的地方，一樣近時選靠人這一邊的。
    rAthena 目的地不能走或路太長就整個不動，這裡只有一步都走不出去、或路長下限超過上限時才不動
  - 上限：一次最多展開 `max_search_nodes` 2048 格，rAthena 的節點表是 `MAX_WALKPATH` 32 的平方 1024 格，地窟 3 公尺寬的走廊繞一圈常常超過 1024 所以放寬一倍；路長最多 `max_path_cells` 96 格 48 公尺，rAthena 是 `MAX_WALKPATH` 32 格、玩家點地 `max_walk_path` 17 格，這裡的鏡頭看得到約 15 公尺，繞一棟房子要多留；搜到上限還沒找到就走到搜過的格子裡離目的地最近的那一格
  - 每張地圖在讀進來時把能走的格子分好連通區塊，兩邊不在同一塊就不用搜尋，直接找最近走得到的地方
  - 每個實體算路有額度：每秒補 `budget_per_second` 4096 格、最多存 `budget_max` 4096 格，用完之後這一次只搜剩下的格子。客戶端預測照同一條規則扣，連點時兩邊搜到的格子數一樣
  - 沿路走時中途點走到了就用這一 tick 剩下的距離接著往下一個點走，一次走多遠、分幾次走，路線都一樣；離終點 0.1 公尺內、完全走不動、或沒有路就停下
  - 量到的耗時，Xeon 2.1GHz 單執行緒：一次搜到上限 2048 格約 8 毫秒；各地圖隨機點 2 到 15 公尺，p99 展開 260 格以內，平均 0.2 到 0.6 毫秒；
    晨曦鎮惡意客戶端每 tick 送一個最難算的目的地，額度擋住之後平均每 tick 2.3 毫秒、最慢 6 毫秒，一秒最多花在這個人身上約 18 毫秒。
    建格子和連通區塊一張圖 11 到 23 毫秒，伺服器在 `set_blockers`、客戶端在收齊 `world.blockers` 時先建好，不會卡在第一次點地。
    數字由 `tests/test_path_finder.gd` 的 `test_worst_case_search_time` 和 `tests/test_path_sync.gd` 的 `test_hostile_move_targets_are_capped_per_player` 印出來
  - 關卡底線：`test_every_map_portal_and_npc_is_reachable_on_the_grid` 驗每張地圖從出生點和傳送落點，在格子上走得到每個傳送點、存檔點、NPC；格子畫得太保守把通道堵死會紅
  - 攻擊時序照舊是毫秒精度，只有移動對齊 tick 邊界；同一段時間分幾次 `step` 結果都相同
  - 伺服器每 tick 用 `movement_states()` 取得 `{id, position, velocity, moving}` 組 `entity.state`
  - 客戶端永遠不能設定位置；現在客戶端的 `set_position` 只留給單機測試工具，正式流程禁止
  - `set_position` 受 `allow_external_position` 控制，預設值 `ALLOW_EXTERNAL_POSITION` 為 true 讓單機表現層還能跑；伺服器建立地圖的 BattleWorld 後必須設成 false
- **追擊、回家、鎖定走近被擋住時也尋路**，2026-09-27 加，程式在 `BattleWorld._follow_chase_path`，數字在 `pathfinding` 區 `chase_` 開頭和 `map_tick_budget`
  - 怪物追人、怪物回出生點、玩家鎖定攻擊走近都用它；逃跑、kite 往後退、閒晃、巡邏照舊直線走，行為規格見 `docs/怪物行為.md`

  - 尺寸推導：鏡頭是 15 度長焦、俯角 38 度、距離 24～64 公尺，拉到最遠時畫面邊緣離角色約 15 公尺；
    （俯角 2026-09-22 改成 45 度、距離上限改成 52，都讓實際視野**變小**，所以這個格子尺寸只會更保險，不用重算）3×3 格保證至少 16 公尺，最遠 24 公尺，畫面裡的東西一定在視野內。RO 的視野是 rAthena `src/common/mmo.hpp` 的 `AREA_SIZE 14` 格，用走路速度換算一格約 0.5 公尺，14 格約 7 公尺；這裡鏡頭看得比 RO 遠，格子跟著放大到相當於 30 格
  - 每個 tick 先重算每個人的視野，進入視野推 `entity.spawn`、離開推 `entity.despawn`，客戶端本來就會處理這兩種訊息；死掉的怪物進視野時 spawn 帶 `alive: false`
  - 後到的人看到的要和一直看著的人一樣：`entity.spawn` 帶進視野當下還在持續的狀態，坐著、身上的狀態和印記、詠唱、怪物蓄力、Boss 範圍預告、面向；進地圖時地上已經有的陷阱、範圍效果、隕石、符補送一批 `ground_spawn`，帶 `existing: true`；斷線接回時自己身上的增益補送 `buff_start`，也帶 `existing: true`。RO 也是這樣，rAthena `src/map/clif.cpp` 單位進視野的 `clif_set_unit_idle` 帶面向和 dead_sit 坐姿，`clif_getareachar_unit` 接著補狀態圖示，地上的技能單位由 `clif_getareachar_skillunit` 補送。2026-09-27 加，`tests/test_server_lasting_state.gd`
  - 已經看到的實體離開 3×3 格之後還要再遠 `AOI_LEAVE_MARGIN_M` 4 公尺才消失，在格子邊線來回走不會一直生成又消失
  - `battle.event` 只送給看得到當事人的玩家，當事人欄位是 entity、attacker、target、caster、player、killer、to，欄位是 -1 代表沒有對象、不算當事人，掉落物事件看掉落物在不在視野裡；地上的東西 ground_spawn、ground_trigger、ground_remove 不看視野整張地圖都送，陷阱被視野外的人踩到時旁觀的人也看得到炸開；`entity.state` 只包含視野內的實體，自己一定在裡面；只送當事人的私人事件不受視野影響
  - `chat.say` 的 local 頻道只有視野內聽得到，Boss 公告這類系統訊息照樣全地圖或只給本人
  - 實測 100 隻閒晃怪物的 80×80 公尺地圖，一個玩家：整張地圖廣播進場 15013 B、每秒 52991 B；視野格子進場 6387 B、每秒 22048 B，`tests/test_security_aoi.gd`
  - GameServer 的 `aoi: false` 選項會關掉視野改成整張地圖廣播，只給測試比較流量
- **客戶端顯示**
  - 自己：按下移動立即預測，收到伺服器位置後若差距超過 0.12 公尺就在 0.15 秒內平滑拉回

## 5. 防串改與防作弊清單
| 類別 | 做法 |
|---|---|
| 位置作弊 | 伺服器算位置和路；move.to 目標超出地圖邊界拒絕，在不可行走區裡推到最近站得住的地方；每 tick 移動量不超過速度×時間，沿路轉彎時也是 |
| 尋路拖垮伺服器 | 連送很遠、圍起來、在牆裡的目的地：每次搜尋最多 2048 格、路長最多 48 公尺，每個人每秒最多 4096 格的額度，同一個 tick 只算一次；鎖定攻擊走近也吃同一份額度；怪物追擊整張地圖每 tick 512 格；見第 4 節 |
| 自己換地圖 | 客戶端沒有任何指定地圖的訊息；換地圖只由地圖 tick 判定傳送點範圍或死亡復活觸發；char.enter 只能進存檔裡的地圖，不合法時回預設地圖出生點 |
| 安全區開打 | 城鎮這類 safe_zone 地圖拒絕 act.attack 和攻擊類 skill.use，回 safe_zone |
| 加速外掛 | 攻擊間隔、技能冷卻、道具冷卻全部由伺服器時鐘判斷；客戶端送得再快也沒用 |
| 斷線重置冷卻 | 離開地圖時把還沒結束的攻擊間隔、出手動作、技能冷卻、施法後延遲、道具冷卻換算成伺服器 unix 毫秒的結束時間存進角色紀錄的 `cooldowns` 欄位，重進、換地圖、伺服器重開後都扣掉經過的時間套回，最多套回 10 分鐘防時鐘被調；套回之後把還在冷卻的技能用 `skill_cooldowns` 推給本人，快捷列的遮罩才跟伺服器一樣；rAthena 的 `skill_cooldown_save` 也是存到資料庫；NPC 治療只補 HP 和 SP，不重置攻擊時序 |
| 戰鬥中拔線躲死 | 10 秒內打過人或被打、身上有怪物鎖定、自己還鎖著目標時斷線，角色停止動作但留在地圖 10 秒，照樣會被打死；死亡或時間到才存檔離開，寫 `char.linger`、`char.linger_end`；同帳號在這段時間重新進入同一個角色直接接回原本的實體，重送 world.enter 和視野；照 rAthena `conf/battle/player.conf` 的 `prevent_logout: 10000` |
| 占著連線 | 握手完成後 30 秒沒登入踢 `login_timeout`；登入後 20 秒沒收到任何訊息推 `heartbeat`，客戶端回 ping，60 秒都沒訊息踢 `idle_timeout`，和 rAthena conf 的 `stall_time: 60` 一樣；同一個 IP 的 Session 上限 10 條，傳輸層擋第一道、`game_server.create_session` 擋第二道，超過的回 `too_many_connections` |
| 封包洗頻 | 每個連線 token bucket：全部訊息每秒 30、act.* skill.* item.* 每秒 8、chat 每秒 2、party.* 每秒 3、trade.* friend.* block.* 每秒 5、auth.login 每 10 秒 3、char.create 加 char.delete 每 10 秒 5、server.list 每 10 秒 5；超量記一次違規，5 秒內違規 20 次踢線。密語走 chat.whisper，和一般聊天共用每秒 2 則的桶 |
| 換連線繞限流 | 依來源限制：每 10 秒新連線 30 條、每分鐘登入嘗試 30 次、每小時自動註冊 20 個帳號、同時算密碼雜湊 2 個；同時連線每個來源 10 條。來源是 IPv4 位址本身，IPv6 照 /64 前綴算同一個，一般一戶人家或一台雲端主機就拿到一整段 /64，裡面的位址可以隨便換，照單一位址算等於沒有限制；IPv4 對應位址 `::ffff:a.b.c.d` 換回 IPv4。登入鎖定和 IP 封鎖也照來源算，稽核寫原本的位址。前綴長度用 `--ipv6-prefix` 調。實作在 `server/security/ip_source.gd`，`game_server.source_key` 是唯一入口 |
| 假封包 | 每種訊息逐欄位驗證型別、範圍、長度；未知類型記違規；JSON 解析失敗直接斷線；字串欄位拒絕 C0、C1 控制字元、雙向文字控制、行分隔和段分隔、代理區、非字元；JSON 的 `\u0000` 跳脫在解析前擋掉，否則 Godot 每次都會印一行引擎訊息 |
| 重放 | 請求 id 必須遞增；token 綁連線，重新登入後舊 token 失效 |
| 竄改存檔 | 存檔只在伺服器端的 `server_data/` 目錄；每筆紀錄附 HMAC-SHA256 簽章，密鑰來自環境變數或伺服器端 `server_secret.key`，不在客戶端；讀取時簽章不符就隔離該檔並記錄，不載入 |
| 寫入中斷 | 原子寫入：先寫 `.tmp`、關檔、再 rename 取代；保留上一版 `.bak` |
| 用舊備份回溯 | 每筆紀錄有遞增的 `version`，簽章包含它；寫成功後把「紀錄名稱 版本」附加到 `journal/versions.log`，每行帶 HMAC；讀到簽章正確但版本比日誌舊的檔案就是拿 `.bak` 蓋回來的回溯，隔離並寫 `db.rollback`，不載入。正式檔壞掉或不見但 `.tmp` 還在時 `.bak` 只准比日誌少一版，用它復原會重寫成新版本；正式檔和 `.tmp` 都不見只剩 `.bak` 不是當機會留下的樣子，一律要和日誌同版。舊的 schema 1 檔沒有版本，讀得到、算第 0 版，下次寫入升成 schema 2 |
| 複製道具 | 道具操作只在模擬的單一 tick 內完成；存檔取 tick 邊界的快照 |
| 玩家交易複製道具 | 交易紀錄只在記憶體、永遠不存檔，任何一方斷線整場消失；擺出來的道具、指名的裝備和金幣當場押住，交易結束前賣、丟、用、穿、精煉、存倉庫、花錢、再擺一次都動不到，見下方「交易押住」；擺出來的東西在確認的當下重新比對背包和押住，改動讓版本加一並清掉兩邊的確認，舊版本的確認回 stale_offer；交換前在背包的複本上試做，格子、負重、金幣上下限都過了才套用，全有或全無；換完先寫 trade.done 稽核再改東西，兩邊立即存檔，見 docs/社交系統規格.md 第 2 和第 7 節 |
| 竄改存檔裡的好友名單 | 好友和封鎖名單存在帳號紀錄，和倉庫一樣有簽章和版本日誌，改過整份隔離，連登入都會失敗；讀回來還會再過一次 sanitize，壞掉的項目丟掉、超過上限的截掉 |
| 用交易和密語騷擾 | 交易邀請、好友邀請、封鎖每秒 5 則，同一個人連續邀請至少隔 1 秒，被邀請的人同時只有一個邀請；密語和一般聊天共用每秒 2 則；封鎖之後對方的密語和兩種邀請都到不了，而且回應和「對方不在線上」一樣，封鎖了誰不會外流 |
| 複製精煉過的裝備 | 帶著精煉或詞綴的裝備每一件在背包、倉庫、交易裡各自一格，永遠不和同款疊在一起；用道具 id 找東西的路徑一律只找得到可以疊的那一格，要動到某一件一定要給 uid，所以「賣掉一疊順便把 +9 的那把也算進去」這種事不會發生。存檔讀回來時重複的 uid 會重新給號，見 docs/裝備成長.md 第 1 節 |
| 偽造精煉結果 | 成功率、擲骰、材料和金幣全部在伺服器；`item.refine` 的 schema 只留 uid、item_id、protect 三個欄位，多送的 outcome、refine、success_percent 在驗證時就丟掉；費用在擲骰之前就扣，看到結果才拔線也不會退費 |
| 竄改存檔裡的精煉和詞綴 | 讀存檔時 `ItemMods.sanitize` 照道具資料重新檢查：稀有度不認得就退回普通、精煉壓回該稀有度的上限、詞綴只留掛得上這個部位又符合稀有度門檻的、數值壓回該裝備的擲骰範圍、超過格數的截掉、uid 不合法就換一個；穿在沒穿東西的格子上的孤兒狀態整個丟掉 |
| 金錢和倉庫 | 金幣只在伺服器透過 `game_server.change_gold` 增減，每次寫稽核；買賣、存取都要先和 NPC 對話並保持在 3 公尺內；倉庫存在帳號紀錄裡簽章，同帳號同時只有一個角色在線；先存角色再存倉庫，中途當機頂多東西消失不會複製，見第 13 節 |
| 搶別人的掉落 | 掉落後 3 秒只有擊殺者能撿，照 rAthena item_first_get_time；同隊伍而且開啟道具分配的成員也能撿，見 docs/隊伍規格.md 第 5 節 |
| 隊伍越權和吸經驗 | 邀請、踢人、轉讓、改分配方式每則指令都重新檢查隊長身分；經驗和道具只分給同地圖、活著、24 公尺內的成員，等級差超過 15 級整隊不分；離開再加入排到輪流分配的隊尾 |
| 竄改隊伍存檔 | 隊伍紀錄和角色檔一樣有 HMAC 簽章和版本日誌，改過的移到隔離區不載入；角色存檔沒有隊伍欄位，改角色檔偽造不了隊伍 |
| 逼伺服器寫檔 | 因為升級、換裝要求的立即存檔每個角色至少隔 1 秒，間隔內的變動留到時間到再存；登出、斷線、轉職照樣立即存 |
| 偽造任務進度 | 打怪只算給擊殺者、買賣只算成交、用道具只算真的用掉的那次；收集、學技能、職業等級不存數字，每次從角色和背包現算；接任務和交任務都要站在對的 NPC 三公尺內，獎勵在同一個指令裡發完並立即存檔，詳見 `docs/任務規格.md` 第 5 節 |
| 追查異常 | 稽核日誌 append-only：經驗變化、道具增減、裝備、轉職、登入 IP，每行 JSON 帶時間和角色 id；撿取、使用、穿脫在指令成功當下寫，玩家同一瞬間斷線也不漏記 |
| 安全稽核 | 踢線 net.kick、違規 net.violation、10 秒內被規則拒絕 100 次以上的 net.suspicious、登入失敗 auth.login_failed；同一種事件同一個來源每分鐘最多 10 筆，全部合計每分鐘 300 筆，被擋下的筆數寫成 audit.suppressed 總結；連線、離線的主控台訊息每 10 秒最多 20 行 |
| 洗遊戲稽核 | `audit_player` 每個帳號每分鐘最多 300 筆、全部合計 6000 筆，正常玩法一分鐘幾十筆；超過的只數筆數，時間窗結束寫一筆 `audit.dropped {account, count, events: {事件: 筆數}}`，帳號太多時其餘合併成一筆 |
| 暴力破解 | 帳號本身永遠不鎖，知道別人帳號的人鎖不住對方。帳號加 IP 的組合 5 分鐘內失敗 5 次鎖那個組合 5 分鐘，回 `locked`；IP 5 分鐘內對任何帳號失敗 7 次封 IP 5 分鐘，回 `ip_banned`，對的密碼也擋；同一個帳號 5 分鐘內被 3 個以上 IP 猜就寫一筆 `auth.account_under_attack`。照 rAthena `conf/login_athena.conf` 的 `dynamic_pass_failure_ban`：只依 IP 封，interval 5 分鐘、limit 7 次、duration 5 分鐘 |
| 密碼雜湊 | PBKDF2-HMAC-SHA256，照 RFC 8018 用引擎內建 HMAC 自己組，輪數照 OWASP 2023 的 600000 次，鹽 16 位元組，輸出 32 位元組。帳號紀錄的 `password_hash` 存 `pbkdf2_sha256$輪數$鹽$雜湊`，鹽和雜湊是小寫十六進位，演算法和輪數跟著紀錄走，之後要加輪數或換算法不用動舊資料。舊格式是 `salt` 欄位加一次 SHA-256，登入成功當下改存新格式、拿掉 `salt`、寫 `auth.password_rehashed`；輪數比目前設定少的新格式也一樣升級；密碼錯不升級。格式不對的紀錄回 `account_unavailable` 並寫 `auth.bad_password_record`，不算猜錯；輪數超過一千萬當格式壞掉，避免一次登入算很久。比對一律走 `timing_safe.gd`。一次雜湊約 0.8 秒，所以在 WorkerThreadPool 用高優先工作算，登入是非同步回應；低優先工作只分到執行緒池三成的執行緒，4 核機器只有 1 條，四個同時登入會排隊算：版本、每個 IP 的登入限速、鎖定、並發上限、讀帳號、格式檢查都在主執行緒當場做完，沒過直接回失敗，不佔背景名額；過了才丟進背景，`Session` 先不回應，主迴圈每幀 `auth.poll` 收掉算完的，比對結果、升級寫檔、存登入時間、踢舊連線、回應全部回到主執行緒做，背景只算雜湊不碰伺服器狀態，鹽也在主執行緒產生。同時在背景算的名額全服預設 CPU 核心數減 1、至少 2，留一個核心給主迴圈；每個來源預設 2 個，網咖或同一個出口的兩個人一起登入不會被擋；三個數字都是伺服器設定，見第 2 節登入名額設定。超過回 `server_busy`，客戶端隔 1～2 秒的隨機時間自動重送一次，還是忙碌才顯示給玩家；重送前本機的登入限流不夠一次就等到夠，不會變成本機的「太頻繁」。同一條連線還在算又送登入直接回 `login_pending`，不排隊，正常客戶端會等回應不會遇到。算到一半斷線或關機：結果丟掉，不建帳號、不升級、不寫登入時間；只有猜錯會照樣記進記憶體裡的鎖定次數，猜完馬上斷線逃不過。同帳號同時兩個登入可以一起算，各自算完照先後收尾，後完成的踢掉先完成的；兩個都要升級時只升一次。同名同時註冊，後來的回 `server_busy`。收尾時重新讀帳號紀錄，只改雜湊和登入時間，背景算的期間存過的倉庫之類的欄位不會被舊資料蓋掉。實測見第 11 節仍存在的風險下面那段。測試在 `tests/test_security_password.gd`，測試伺服器用 `password_iterations` 選項調低輪數 |
| 重複登入 | 同帳號第二個連線登入時踢掉第一個，並先存檔 |
| 客戶端版本 | 登入時比對 client_version，不符拒絕。現在是 `Protocol.CLIENT_VERSION` 0.9.8，2026-09-27 技能加了 requires_buff、consumes_buff、self_debuff：`skill_failed` 和 `skill_cast_cancel` 多一個原因 no_buff，`buff_end` 多一個原因 consumed，普攻命中回血的 heal 事件 skill_id 改成實際的來源；舊客戶端會把 no_buff 當字跳出來，所以升上來。0.9.7 是同一天 `npc.choose` 轉職失敗改回細分的原因代碼加 `params`，不再只回 `job_change_failed`；舊客戶端看不懂新代碼，所以升上來。0.9.6 是同一天進地圖、換地圖、斷線接回推 `skill_cooldowns`，客戶端換地圖時丟掉舊地圖時鐘的冷卻改等這則，斷線接回補送自己詠唱到一半的 `skill_cast_start`，`ground_trigger` 改成整張地圖送；新客戶端連舊伺服器換地圖會看不到冷卻，所以升上來。0.9.5 是同一天 `entity.spawn` 多帶面向和持續狀態、進地圖補送地上的東西；0.9.4 是同一天交易押住讓 `self.inventory` 的 items 改成扣掉押住的數量。舊客戶端連不上新伺服器 |

## 6. 存檔時機
- 資料有變動就標記為髒資料，每 60 秒寫一次

- 登出或斷線時立即存
- 伺服器關閉時全部存完才退出

## 8. N4 實作備註，給 N5 客戶端
### 進入流程
1. 連線 `ws://127.0.0.1:7777`，送 `auth.login`，`client_version` 用 `Protocol.CLIENT_VERSION`
2. `server.list`、`char.list`、`char.create`、`char.delete` 照舊，回應格式同 mock_backend；伺服器列表的欄位見第 3.1 節
3. `char.enter` 的回應 `{ok, character_id, map, self_id}` 一定先到，接著依序推送
   `world.enter` → `world.blockers` → `world.colour` → `self.inventory` → `self.stats` → `quest.state` → 視野內每個其他實體一則 `entity.spawn`，包含掉落物 → 地上已經有東西時一則 `battle.event`，裡面是帶 `existing: true` 的 `ground_spawn` → 自己有技能還在冷卻時一則 `battle.event`，裡面是 `skill_cooldowns`；視野外的等走近才會收到。換地圖時從 `world.enter` 開始照同樣的順序再推一次
4. 之後每 50ms 一個 tick，同一個 tick 內的推送順序：`entity.spawn`、`entity.despawn`、`battle.event`、`entity.state`、`self.stats`、`self.inventory`、`quest.state`；走動時進出視野的實體也用 `entity.spawn`、`entity.despawn`
5. 沒有登出訊息，斷線就是登出，伺服器立即存檔；戰鬥中斷線角色會留在地圖 10 秒，這段時間同帳號 `char.enter` 同一個角色會直接接回，回應和推送和第一次進入相同，最後多一則 `battle.event` 補送自己的狀態，依序是身上還在的增益 `buff_start`、詠唱到一半的 `skill_cast_start`，都帶 `existing: true`，詠唱的 cast_ms 是剩下的時間，再來是 `skill_cooldowns`；在地圖裡不能送 `char.*`，要回角色選擇就重新連線
6. 登入後 20 秒沒送任何訊息會收到 `heartbeat`，回一個 `ping` 即可；60 秒都沒訊息會被踢 `idle_timeout`，沒登入的連線 30 秒就踢 `login_timeout`

### 關閉伺服器
- Godot 腳本收不到 SIGTERM，收到就直接結束；正常關閉請建立停止檔，或用 `server/run_server.sh` 啟動
- 客戶端開發模式自動啟動伺服器時，不要用 `OS.kill`，改成建立 `--stop-file` 指定的檔案

## 10. N5 客戶端實作備註
### 啟動
- 主程式 `scenes/login.tscn` → GameClient 連 `ws://127.0.0.1:7777`；開發版連不上時用 `OS.create_process` 啟動 `server/main.gd`，資料在 `user://server_data`，停止檔 `client_launched_server.stop`，遊戲結束時建立停止檔讓它存檔退出
- 帶了 `--server=` 或任何 `--dev-` 參數時一律不自動開伺服器，連不到就照實回 `connect_failed`。
  2026-09-27 Victor 驗收時兩次遇到：指定的 78xx 還沒開好，客戶端就在那個 port 自己開一台，存檔寫到 `user://server_data`，量到的是錯的那一台。
  判斷在 `game_client.gd args_allow_auto_launch`，測試在 `tests/test_server_login_retry.gd`
- 自動開伺服器還要不要留，查過的結果：後台管理器開遊戲一定帶 `--server=ws://127.0.0.1:7777`、`7778` 或 `--offline`，
  使用者平常的流程完全用不到它；AI 驗證也都帶參數。剩下的只有什麼參數都不帶直接開，例如在編輯器按執行，
  那時候連的是穩定版的 7777，穩定版伺服器沒開就會用開發版的程式在 7777 開一台，存檔是第三份 `user://server_data`，
  之後管理器要開穩定版伺服器會因為 port 被佔住起不來。建議整個拿掉，連不到就顯示連不上；還沒拿，等使用者決定
- 手動起伺服器：`godot --headless --path . --script res://server/main.gd -- --port=7777 --data=<目錄> --stop-file=<檔案>`，客戶端連得上就不會自動啟動；要讓別台機器連就加 `--bind=`，規則見第 2 節
- 開發自動流程：`godot --path . -- --dev-page=game` 自動登入 shottest、沒角色就建角、進地圖、攻擊最近的怪；`--dev-target=N` 指定怪物實體 id，`--dev-quit-after-ms=N` 真實時間到了自動結束，`--dev-smoke` 依序測聊天、加點、技能、道具、NPC、移動、打怪撿東西、登出回選角；`--dev-portal` 走進第一個傳送點換一次地圖，`--dev-shots=目錄` 每張地圖存一張截圖，`--dev-shot-distance=N` 截圖時的鏡頭距離
- 單機表現測試：`godot --path . res://scenes/dev/playground.tscn -- --offline`，原本的 `--combattest`、`--autotest`、`--npc-preview` 只在單機模式有效；沒有 `--offline` 又沒進地圖時會回登入頁

### GameClient
- 請求 id 遞增，等待中的請求放字典，預設 8 秒逾時；斷線時全部以 `disconnected` 失敗
- `enter_character` 回傳 world.enter，之後的推送先暫存，`net_session` 接好 signal 才呼叫 `release_pushes`，場景切換期間不會掉訊息
- 本機先用 token bucket 擋頻率：全部每秒 24、act/skill/item 每秒 6、chat 每秒 1.5、server.list 每 2.5 秒 1 次，比伺服器低，避免被記違規
- `list_servers()` 回傳 `{ok, reason, servers, latency_ms}`，servers 每一筆都經過 `server_list.gd` 檢查，latency_ms 是這次請求量到的來回時間；另有 `measure_latency()` 用 ping 量一次
- 伺服器沒有登出和 session 延續，HUD 登出是斷線，回選角頁時用這次執行記在記憶體的帳密重新登入；帳密不寫檔
- 意外斷線或被 kick 發 `disconnected(reason)`，遊戲場景回登入頁顯示原因；自己呼叫 `logout`、`leave_world` 不發

### 同步
- 其他實體：`entity.state` 放進快照緩衝，用 `server_clock` 估計的伺服器時間往前 60ms 取樣內插，沒有新快照時用速度外推最多 100ms；兩個快照隔超過 1.5 個 tick 代表中間停著，補一個停在原地的快照；距離超過 3 公尺或剛 respawn 時不內插直接換位置
- battle.event 收到就播，只有 respawn 和掉落物的出現消失排進佇列等內插時間到了才播；自己在距離內按攻擊時先揮，伺服器的 attack_start 接手，時序契約在 docs/打擊感規格.md
- 自己：移動指令送出的同時用 `prediction.gd` 以伺服器給的 move_speed 預測，指令排在伺服器開始走的那個 tick 邊界才套用位置，算法在第 0 節，面向和動畫立刻反應；收到自己的 entity.state 時和「那個 tick 對應的本機時間」的預測位置比對，差 0.12 公尺以上 0.15 秒內平滑拉回，小誤差每次修 15%，超過 4 公尺直接換位置；**雙方都停著時**誤差在 0.35 公尺以內一次對齊，不再平滑往回拉，並且每 100ms 再對一次
- 攻擊鎖定時伺服器自己把角色往目標移動，本地不預測，位置跟著自己的快照，取樣時間是估計的伺服器現在；按移動、目標死亡的 target_lost 會回到預測模式
- 移動指令：move.dir、move.to 至少隔 50ms 而且內容有變才送；從移動切到 move.stop 立刻送。最壞情況每秒約 22 則以內
- 撿東西走到 1.5 公尺內才送 item.pickup，伺服器回 too_far 時每 150ms 重試，最多 12 次

### 客戶端還沒做的
- 技能圖示還是程式畫的佔位圖，正式特效美術填 `src/world/skill_effects.gd` 的 ART 表
- NPC 對話的治療和轉職效果只看數值推送，治療沒有特效，轉職會換外觀

### 仍存在的風險
- 沒有 TLS：伺服器本身只講 ws:// 明文，密碼和封包可以被竊聽、重放登入封包；`--bind` 綁非本機位址時會印警告，對外開放前面一定要擺做 TLS 的反向代理
- 密碼雜湊已經不擋主迴圈，2026-09-27 實測：自己開伺服器，一條連線登入的同時另一條每 20 毫秒送 ping，登入 826～910 毫秒，
  期間 ping 中位數 4.5～6.6 毫秒、最慢 8.8～14.2 毫秒，改之前是 759 毫秒；那時另一個崗位正在跑全套測試，機器負載接近滿，
  有一次量到最慢 213 毫秒，是 CPU 被搶。不經過網路的量法在 `test_ping_and_tick_do_not_wait_for_hashing`，
  600000 輪算 829 毫秒期間最慢一次 ping 0.21 毫秒、最慢一幀 0.29 毫秒。
- 同一天改成高優先工作、名額照核心數，在 4 核容器重量，當時別的崗位的測試佔著一個核心，負載 3 上下：
  - 只算雜湊，同時 N 個全部算完：低優先 1 個 808～922、2 個 1637、3 個 2360～2406、4 個 3130～3262 毫秒，就是排在同一條執行緒上一個一個算；
    高優先 1 個 822～872、2 個 885～941、3 個 989～1071、4 個 1459～1542 毫秒，4 個比 3 個慢是因為只剩三個核心空著
  - 不經網路，主執行緒照主迴圈的節奏每 10 毫秒跑一幀：3 個同時算時一幀中位 0.08、最慢 3.21 毫秒，沒人登入時最慢 4.67；
    4 個同時算時一幀中位 0.11、最慢 12.41 毫秒，沒人登入時最慢 4.90；ping 處理兩種都在 0.22 毫秒內
  - 自己開伺服器走網路，另一條連線每 50 毫秒 ping：預設名額 3 個同時登入 1139～1201 毫秒，ping 中位 6.9～7.0、最慢 13.8～20.8 毫秒，
    和沒人登入時的中位 6.9 一樣；把名額調成 4 個同時登入 1567～1868 毫秒，ping 中位 6.9、最慢 20.7～48.3 毫秒。
    ping 中位 6.9 是主迴圈每秒 100 幀加上探針自己的幀造成的，不是雜湊。名額等於核心數時主迴圈要和四條雜湊搶 CPU，
    偶爾慢一幀，這就是預設留一個核心的原因
  - 吞吐量：預設 4 核機器同時 3 個、一次約 1 秒，一秒大約處理 3 次登入；大量玩家同時上線時其他人會先拿到 `server_busy`，
    客戶端自動重試一次，還是忙碌才顯示「伺服器忙碌，請稍後再試」。正式機核心多名額就跟著多
- 登入名額還是能被很多來源一起卡住：每個來源每分鐘最多 30 次登入，每次約 1 秒，平均只佔得住半個名額，
  4 核機器的 3 個名額大約 6 個來源一起灌就能一直卡滿，別人會一直拿到 `server_busy`。
  IPv6 已經照 /64 算，一般使用者拿不到很多段；真的遇到要加排隊或驗證碼，正式機核心多名額也跟著多
- IP 封鎖對 NAT 後面的玩家會誤傷：同一個網咖有人猜 7 次密碼，整間都要等 5 分鐘；rAthena 也是這樣，之後可以加白名單或驗證碼
- 分散攻擊只寫稽核不擋：攻擊者用很多 IP 慢慢猜同一個帳號時帳號還是不鎖，靠每個 IP 7 次的封鎖拖慢，密碼太弱還是會被猜到；之後要加驗證碼
- 版本日誌和存檔放在同一台機器，拿到伺服器檔案又刪掉 `journal/versions.log` 的人還是能回溯到任何一版；正式環境要把日誌另外送到別台機器。另外只要把正式檔弄壞、留下 `.tmp`，`.bak` 就能回溯一版，這是為了讓真的寫入中斷還能復原，最多損失最後一次存檔的差異
- 帳號檔被回溯時整個帳號登不進去，要管理者從隔離區處理；沒有自動修復
- 戰鬥中斷線留在地圖 10 秒期間角色不會動也不會反擊，被圍住一定會死；RO 也是這樣，之後有 PvP 時要決定要不要讓它繼續自動攻擊
- 視野格子只做在伺服器推送，怪物 AI 還是整張地圖跑；地圖大到幾百隻怪時要把 AI 也分格
- 遊戲稽核每個帳號每分鐘 300 筆的上限比正常玩法高很多，但一分鐘內超過的紀錄只剩總結裡的筆數，查案時看不到明細；量大時要改成批次寫入或換資料庫
- 自動註冊：每個 IP 每小時 20 個帳號，多 IP 還是能慢慢塞，正式環境要改成網站註冊或加驗證
- 掉落擁有權只給擊殺者和開著道具分配的隊友，rAthena 的第二、第三順位還沒做
- 隊伍只在同一台伺服器內有效，跨伺服器隊伍和小地圖上的隊友位置點還沒做，見 docs/隊伍規格.md 第 9 節
- 買賣和存取每次成功都寫兩三筆稽核，每條連線每秒最多 8 次，量大時同上要批次寫入
- 精煉和製作的擲骰用地圖的 rng，同一張地圖上兩個人同時精煉會互相影響彼此抽到的序列；不影響機率，但要重現某一次結果時要連同順序一起記
- 精煉過的裝備賣給 NPC 只拿基礎售價，投資完全拿不回來；之後要加價之前要先想清楚會不會變成洗錢管道
- 裝備爆掉沒有任何復原管道，管理者也只能從稽核看到它存在過；誤觸由介面的確認框擋，之後要做客服補償就要靠那筆稽核
- 隱藏區域只是不送 `zones`，玩家還是可以用座標走過去；這是設計上的「不標出來」而不是「進不去」

## 12. 多地圖、傳送點與存檔點

2026-09-16 加。地圖資料格式擴充在 `src/core/map_data.gd`，碰撞在 `src/core/map_collision.gd`。

### 地圖檔 data/maps/<id>.json
| 欄位 | 內容 |
|---|---|
| name | 顯示名稱 |
| scene | 客戶端的場景產生器，目前是 meadow 或 town，對應 `src/world/map_scenes.gd` |
| bounds | 可行走範圍 |
| player_spawn | 新角色和存檔位置不合法時的出生點 |
| safe_zone | true 代表城鎮，不能戰鬥 |
| spawns、npcs | 怪物和 NPC 擺放，位置要可以走；單隻怪可以加 `patrol` 巡邏路線，2～12 個可以走的點 |
| zones | 設計好的區域 `{id, name, center, radius, hint, hidden}`，只給介面顯示名稱；`hidden` 的不送給客戶端 |
| portals | `{id, position, radius, to_map, to_position}`，玩家走進 radius 內由伺服器換地圖；2026-09-16 起沒有 require_level，誰都走得過去 |
| props | 客戶端的靜態擺設 `{model, position, rotation_y, scale}`，model 是 `res://assets/` 底下不含副檔名的路徑 |
| blockers | 不可行走區，`{type: "rect", min, max}` 或 `{type: "circle", center, radius}`，房屋和城牆用 |

- 驗證：出生點、怪物、NPC、傳送點都不能在 blockers 裡；傳送點半徑 0～5 公尺；
  目的地地圖要存在、目的地座標要可以走、而且不能落在對面的傳送點範圍裡，否則伺服器啟動時把那個傳送點停用
- 擺設模型只能是英數、底線、減號和斜線組成的相對路徑，不能有 `..`，避免地圖檔被當成任意讀檔

### 伺服器
- `GameServer` 預設載入 `town` 和 `meadow`，每張一個 `MapInstance`，新角色的出生地圖是 `town`，和 `mock_backend.STARTING_MAP` 一致
- 換地圖只有兩個來源，都在地圖 tick 結束後才做：玩家站進傳送點範圍、玩家自己送 `act.revive` 而存檔點在別張地圖
- `transfer_player` 的順序：記下剩餘冷卻 → 結束對話 → 從舊地圖移除並廣播 entity.despawn → 在新地圖生成並推送 world.enter → 套回冷卻 → 寫 `map.transfer` 稽核 → 立即存檔
- 存檔點：角色存檔多了 `save_map`、`save_position`，晨曦守護者的對話選項 `save_point` 登記目前站的位置；
  地圖不存在或位置不能走時退回預設地圖出生點
- 死亡：照 rAthena `pc_dead` 在死亡當下扣經驗，扣目前等級升級所需經驗的 1%，初心者不扣，寫 `exp.death_penalty` 稽核；
  不會自動復活，人躺在倒下的地方等玩家自己決定，規格在第 14 節
- 移動碰撞：`BattleWorld` 的移動、鎖定攻擊走近、怪物閒晃和擊退都走 `map_collision.gd`，碰到不可行走區沿邊滑動，
  一次移動很遠也不會穿牆；`move.to` 目標在不可行走區裡推到最近站得住的地方再尋路走過去，見第 4 節
- `push_out` 推最多 4 輪還在牆裡就改找尋路格子裡最近一整格都能走的格子。以前沒有輪數上限，晨曦鎮地圖角落要推五萬多次、38 毫秒，
  最後還是停在牆裡；伺服器每收到一則 `move.to` 都推一次。現在每張地圖任何一點最多 0.9 毫秒，推出來一定站得住
- 安全區：`safe_zone` 地圖拒絕 `act.attack` 和 `active_target`、`active_ground` 類技能，自身增益和補血照常

### 世界地圖、等級限制與傳送員
2026-09-16 加，地圖圖和怪物表在 `docs/世界地圖規劃.md`。
- 地圖檔多了 `level_range`、`warp_allowed`、`save_point`、`paths`、`layout`（`require_level` 在 2026-09-16 拿掉，世界不擋等級），怪物可以寫成一群 `{monster, count, center, radius}`，位置用地圖 id 和群組編號當種子撒點，伺服器和客戶端算出來一樣；`respawn_seconds` 可以蓋過怪物資料
- `GameServer.DEFAULT_MAP_IDS` 載入六張地圖；傳送點沒有等級門檻，踩到就走，1 級也進得了地窟，死是玩家自己的選擇
- 換地圖時 `BattleWorld.player_buffs` 取出剩餘時間，`apply_player_buffs` 在新地圖套回並發 `buff_start`，每張地圖的模擬時鐘各自獨立所以不能直接帶 until_ms
- 傳送員：對話選項條件 `warp:<地圖 id>`，`player_commands._context` 帶 `warp_targets` 給對話樹過濾；對話動作 `warp:<地圖 id>` 交給 `game_server.request_warp` 驗證地圖存在、允許傳送、去過、等級、不是現在這張、落點可走，通過就登記在 `OnlinePlayer.warp_request`，地圖 tick 結束時和傳送點一樣交給 `transfer_player`，稽核 reason 是 `warp`；被拒寫 `map.warp_rejected`
- 去過的地圖記在角色存檔的 `visited_maps`，進地圖時登記，舊存檔沒有這個欄位時進地圖補上
- Boss：怪物資料 `boss: true` 的實體死亡和重生時全地圖收到 system 公告；`knockback_immune` 讓技能擊退無效；`area_attack` 每個 AI tick 檢查，有目標而且冷卻到了先發 `area_telegraph {entity, position, radius, at_ms}`，時間到再對圓裡的敵人發 `damage`，`skill_id` 是 `area_attack`

### 客戶端
- `world.enter` 的 `scene` 決定用哪個場景產生器，`map_scenes.gd` 找不到時退回草原
- 換地圖流程：`net_session` 收到第二次 `world.enter` 發 `map_change_started`，遊戲場景蓋上讀取畫面淡入、
  釋放舊地圖節點、建新地圖和傳送點標示，再呼叫 `finish_map_change` 套用新地圖並放出暫存的推送，最後淡出
- 讀取畫面是 `src/world/map_loading_overlay.gd`，全螢幕暗色加地圖名稱，顏色和字型取自 `src/ui/ui_theme.gd`
- 傳送點用 `src/world/portal_marker.gd` 畫發光圓環、粒子和目的地名稱；位置和半徑以伺服器送來的為準
- 本地預測共用同一份 `map_collision.gd`，點到房屋時會把目標修到最近可以走的點再送出
- 安全區在本地也會先擋下攻擊並顯示「城鎮內無法戰鬥」，伺服器仍然會再檢查一次

| 舊存檔 | 2026-09-16 改名之前欄位叫舊名字。沒有 `gold` 時 `from_dict` 讀 `CharacterData.LEGACY_GOLD_FIELD` 指的舊欄位，值原封不動搬過去，下一次存檔只寫 `gold`，舊欄位自然消失。舊存檔的簽章本來就是照舊欄位算的，所以照常通過驗證，不會被當成竄改隔離 | test_save_file_written_before_the_rename_keeps_its_money |

### 商店
- 清單在 `data/shops.json` 的 `shops`：`{商店id: {name, npc, items: [道具id]}}`；NPC 對話選項用動作 `shop:<商店id>` 開店，
  伺服器會核對商店的 `npc` 和正在對話的 NPC 一致，資料寫錯開不了店
- 售價是 `data/items.json` 的 `buy_price`，賣給商人是 `sell_price`，沒寫時是買價的一半無條件捨去；`no_sell: true` 或賣價 0 的道具不能賣，
  照 rAthena `itemdb.cpp` `value_sell = value_buy / 2` 和 `NoSell` 交易限制；`sprout_seed` 標了 `no_sell`
- 現在的店：蜜拉的道具店賣紅、橙、綠、藍色藥水，布隆的武器防具店賣小刀、短劍、長劍、法杖、弓、木盾、布衣、涼鞋、帽子，價格照 RO
- `npc.choose` 選了轉職、條件不符時回 `{ok: false, reason, params}`，對話同時結束；代碼和 params 定義在 `src/core/job_change.gd`，
  單機和連線共用同一份判斷，客戶端用 `JobChange.failure_text` 組成「無法轉職：…」：

  | reason | params | 什麼時候 |
  |---|---|---|
  | `job_change_unknown_job` | `{job}` | 目前的職業不在 jobs.json |
  | `job_change_unknown_target` | `{job}` | 對話資料指到不存在的職業 |
  | `job_change_not_next` | `{from, to}` | 目標不在目前職業的轉職路線上 |
  | `job_change_job_level` | `{required, current}` | 職業等級不到 `balance.json` 的 `levels.job_change_level` |
  | `job_change_basic_skill` | `{required, current}` | 初心者的基本技能不到解鎖轉職的那一級 |
  | `job_change_trial` | `{job}` | 轉職考試還沒過 |
  | `job_change_failed` | 沒有 | 對話資料的 `job_change` 動作格式不對 |

  `job`、`from`、`to` 是職業代號，`required`、`current` 是整數；客戶端只取認得的欄位並轉型，數字夾在 0～9999，
  缺欄位時句子不會留下大括號；角色、稽核、存檔在失敗時都不動
- `npc.choose` 選了開店的回應多帶 `shop: {id, name, items: [{item_id, price}]}`，對話同時結束；商店狀態記在 session，
  重新找任何 NPC 說話、換地圖、斷線都清掉
- `shop.buy {shop_id, item_id, count}`：檢查順序是有開店、同一家店、NPC 在同地圖 3 公尺內、活著、數量 1～30000、道具存在、店裡有賣、
  金幣夠、負重和格子放得下，全部通過才扣錢加道具；回應 `{ok, item_id, count, unit_price, total, gold}`，
  背包和金幣的變化由 `self.inventory`、`self.stats` 推送；照 rAthena `npc.cpp` `npc_buylist` 的錢、負重、格子三道檢查
- `shop.sell {item_id, count}`：賣東西不看哪家店，只要有在和商人交易；穿在身上的裝備不在背包裡所以賣不掉，要先脫下；
  賣了會超過金幣上限時拒絕，回 `gold_limit`
- 失敗原因：`no_shop`、`not_in_shop`、`unknown_item`、`bad_count`、`not_enough_gold`、`gold_limit`、`unsellable`、
  `not_in_inventory`、`overweight`、`inventory_full`、`too_far`、`dead`
- 稽核：`shop.buy`、`shop.sell` 各一筆 {shop_id, npc_id, item_id, count, unit_price, total, gold}，加上 `gold.change`

### 帳號倉庫
- 整個帳號共用一個倉庫，存在帳號紀錄 `accounts/<帳號>.json` 的 `storage: {items: [{item_id, amount}]}`，和帳號一起簽章；
  600 格、一格最多 30000，不算重量，照 rAthena `mmo.hpp` `MAX_STORAGE`、`MAX_AMOUNT`
- 要基本技能 6 級，等級從 `data/skills.json` 的 `novice_basic` 哪一級 `unlocks` 有 `storage` 查出來，
  照 rAthena `npc/kafras/functions_kafras.txt` 的 `getskilllv("NV_BASIC") < 6`；對話樹用條件 `unlock:storage` 走到拒絕的節點，
  伺服器每一則 `storage.*` 指令都再檢查一次
- 不收費：RO 那邊每次開倉庫要收 30～60 塊，晨曦鎮的倉庫由鎮上的管理員經營，起始金幣是 0，收費會讓新手用不了
- 對話動作 `storage` 把管理員記在 session，回應帶 `storage: true`；客戶端接著送 `storage.open`
- `storage.open`：回應 `{ok, slots, max_slots}`，內容用 `storage.items {offset, total, items}` 推送，每則最多 100 格，
  600 格一定超過單一訊息 8KB 所以要分批，客戶端收齊 `total` 格才算開好
- `storage.put {item_id, count}`、`storage.get {item_id, count}`：存進去不看負重，拿回來要放得進背包；
  回應 `{ok, item_id, count, held, stored}` 是做完之後背包和倉庫各有幾個，客戶端用它同步本地的倉庫快取
- `storage.close`：倉庫立刻寫回帳號紀錄；沒關就走開、換地圖、斷線也都會寫回
- 存檔順序：`save_player` 先存角色再存倉庫，倉庫用先讀帳號紀錄再只換 `storage` 欄位的方式寫，登入時間和密碼欄位不會被蓋掉；
  中途當機頂多讓剛移進倉庫的東西消失，不會背包和倉庫各留一份
- 同帳號第二條連線登入時舊連線先被踢、踢之前存檔，所以同一個帳號同時只有一個角色能碰倉庫；倉庫第一次用時從資料庫讀進記憶體，
  這段在線期間都用同一份，不會讀到舊資料
- 失敗原因：`no_storage`、`basic_skill_required`、`not_in_inventory`、`not_in_storage`、`storage_full`、`unknown_item`、
  `bad_count`、`overweight`、`inventory_full`、`too_far`、`dead`、`server_error`
- 稽核：`storage.open`、`storage.put`、`storage.get` {item_id, count, held, stored}，讀寫失敗 `storage.load_failed`、`storage.save_failed`

### 頻率和客戶端
- `shop.*`、`storage.*` 和 act、skill、item 共用每秒 8 次的桶，客戶端本地每秒 6 次
- 客戶端 `net_session` 收到對話回應的 `shop` 或 `storage` 就發 `shop_opened`、`storage_opened`，HUD 打開 `src/ui/shop_window.gd`、
  `src/ui/storage_window.gd`；關視窗送 `shop.close`、`storage.close`；金幣顯示在基本資訊和道具視窗
- 單機版 `battle_session` 用同一份 `shop.gd`、`storage.gd` 在本機套用，臨時角色預設 1000 金幣和基本技能 6 級方便測試
- 截圖流程：`godot --path . res://scenes/dev/playground.tscn -- --offline --map=town --dev-open=shop,storage`，
  連線版 `-- --dev-page=game --dev-open=shop,storage`，再加 `sell` 會切到賣出頁

## 14. 死亡、屍體與復活

2026-09-17 改。原本的做法是死後等 3 秒，伺服器自己把人送回存檔點。那樣沒有人救得到誰：
隊友就算有復活技能，屍體早就被系統帶走了。現在死亡是一個狀態，不是倒數。

### 規則
- 玩家死掉就留在倒下的地方，HP 0，`OnlinePlayer.dead_since_ms` 記下時間，寫一筆 `char.death` 稽核
- **沒有任何自動復活**。伺服器不會因為時間到就把人帶回存檔點
- 玩家自己送 `act.revive` 才回存檔點：和傳送點一樣在地圖 tick 結束時處理，存檔點在同一張地圖就原地復活，
  在別張地圖走 `transfer_player`，reason 是 `revive`，HP 補滿
- 死亡懲罰：死亡當下扣目前等級升級所需經驗的 1%，基本等級 10 以下不扣；被隊友用復活術救起來時退回去，稽核記 `exp.death_refund`；自己回存檔點就不退
- 別人可以救：同一隊的玩家對屍體放復活術，屍體在**原地**站起來，補回技能等級對應比例的 HP
- 唯一的時間限制是 `MapInstance.DEAD_SESSION_LIMIT_MS`，目前 10 分鐘，這是伺服器衛生用的，不是把人送回存檔點：
  連續倒著超過這個時間會被踢線，reason 是 `dead_too_long`，角色照一般流程存檔離開地圖，**存檔裡人還是死的**

### 斷線與重登
- 死著斷線：照一般流程存檔離開，存檔的 `map` 和 `position` 就是屍體的位置，HP 是 0
- 重新登入：在屍體原本的位置生成，人還是死的，`self.stats` 的 `alive` 是 false，客戶端立刻把確認視窗叫回來；
  兩個選擇都還在，可以繼續等人救，也可以送 `act.revive` 回存檔點
- 戰鬥中斷線留在地圖的角色死掉時照舊交給 `finish_linger`，不受這一節影響

### 別人看得到屍體
不另外開通道，走既有的視野廣播：
- `entity.spawn` 本來就帶 `alive`，走進視野時 false 代表這是一具屍體，客戶端播倒地姿勢
- 死亡當下的 `battle.event` 有 `death`，視野內的人都收得到
- 死人不在 `movement_states` 裡，所以 `entity.state` 不會再送他的位置，屍體不會漂移

### 復活術
- 技能資料有 `revive` 區塊就是復活術，程式只看這個區塊，不看職業，目前掛在神職者身上
- 目標規則在 `BattleWorld._revive_target`：同一隊、是玩家、已經死了、不是自己，再加技能射程
- 詠唱結束時 `_revive_by_skill` 在屍體原本的位置把人救起來，HP 補回等級資料的 `revive_hp_percent`，
  發 `respawn` 事件並多帶 `by`，也就是救人的實體 id；伺服器寫 `char.resurrected` 稽核
- 復活術不算攻擊技能，安全區地圖照樣能用
- `skill.use` 的目標檢查：一般攻擊技能只能指定怪物，復活術只能指定玩家，是死是活交給 `BattleWorld` 判

### 客戶端
- `self.stats` 的 `alive` 由 false 變 true 或反過來時 `net_session` 發 `death_state_changed`，
  死著進地圖時也發一次；HUD 收到就開關 `src/ui/death_window.gd`
- 死亡視窗只有標題「你倒下了」和兩個按鈕：**回到主城** 送 `act.revive`，**關閉** 只把視窗收起來，人留在原地。
  沒有說明文字，沒有倒數。關掉之後按任何鍵或點畫面會再叫出來，關閉不等於放棄回主城
- 客戶端永遠不自己判定復活：視窗只送要求，是死是活一律等伺服器推的 `self.stats` 和 `respawn`
- 快捷列上的復活術由 `net_session.use_skill` 自動找最近的一具同伴屍體當目標，找不到就提示附近沒有倒下的同伴

### 測試
`tests/test_server_death.gd`，七個案例：屍體不動也不會自動復活、要求才回存檔點、
別的客戶端看得到屍體並在原地救起來、復活術拒絕自己和活人和怪物和太遠的目標、
死著的客戶端不能動也不能宣告自己活了、死著斷線重登還是死在原地、躺太久被踢線之後重登人還是死的。
