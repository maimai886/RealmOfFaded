# Realm of Faded 打擊感規格

2026-09-15 訂。使用者試玩後說「打擊感不順暢，很慢然後很僵」，先量再改，改完再量。
這份文件是戰鬥表現的時間契約：伺服器事件、客戶端預測、角色外觀元件三方都照這裡走。
數值出處見 `docs/歷史/參考規格.md` 第 2.6 節和第 3 節，量測工具是 `src/dev/combat_probe.gd`。

## 1. 量測方法

```
連線：godot --path . --resolution 1280x720 -- --dev-page=game --dev-timing --dev-quit-after-ms=100000
單機：godot --path . --resolution 1280x720 res://scenes/dev/playground.tscn -- --offline --dev-timing
逐幀：godot --path . --resolution 1280x720 --write-movie <目錄>/f.png --fixed-fps 30 --quit-after 420 res://scenes/dev/playground.tscn -- --offline --dev-timing
```

探針走到怪物旁邊 1 公尺，點怪物開打，記錄自己 5 次揮擊每個階段的本機微秒時間，
再做點地移動、方向鍵移動轉向放開，同時每幀記錄怪物畫面位置和最新伺服器位置的距離、幀時間。
時間點由 `net_session.gd`、`battle_session.gd` 的 `probe_mark` 送出，平常 `probe_enabled` 是 false，不花時間。

量測時機器上另外開著 Blender、Godot 編輯器和其他測試，負載平均約 6，8 核。
兩次量測的幀時間都是穩定的 8.3ms，也就是 120Hz 垂直同步，沒有超過 33ms 的幀，所以卡頓不是效能問題，是設計上的延遲。

連線模式，本機伺服器，來回時間約 8ms，Lv2 初心者 adelay 1379ms、amotion 690ms。單位毫秒。
這張表量的是時序管線，量完之後攻速才改成 RO Renewal，改完的攻速數字在「攻速改照 RO Renewal」那一節。

連線 120fps 的紀錄是相隔 81～85 幀，同樣是 675～708ms。截圖對照在 scratchpad 的 `combat_out/contact_swing.png`。

單機模式改前就沒有事件延遲，改的是移動：原本起步和停下有指數平滑，轉向要 118ms、停下多滑 0.23 公尺，現在按下就走、放開就停。

### 攻速改照 RO Renewal

量完之後決定攻速完全照 RO Renewal，原本自訂的 base_attack_delay 1.4 秒沒有依據，AGI1 DEX1 算出 adelay 1379ms 是「很慢」的一部分。
公式和職業基礎表在 `docs/歷史/參考規格.md` 第 2.6 節，實作在 `Formulas.player_aspd`、`Formulas.amotion_ms`、`Formulas.player_attack_delay`，
武器種類來自 `items.json` 的 `weapon_type`，職業基礎值來自 `jobs.json` 的 `aspd_base`，怪物維持 `monsters.json` 自己的 attack_delay。

| 角色 | 改前 | 改後 |
|---|---|---|
| Lv1 初心者 AGI1 DEX1 拿初心者小刀 | adelay 1379ms、amotion 690ms | ASPD 141，amotion 590ms、adelay 1180ms，和 rAthena 一樣 |
| 探針實測，連線模式，Lv2 初心者 | 揮擊 → 傷害 687ms，揮擊間隔 1383ms | 揮擊 → 傷害平均 586ms，揮擊間隔平均 1184ms，點擊 → 揮擊 0.1ms，預測揮擊 30ms 後被伺服器確認 |

原本以為 RO 的 Lv1 初心者是 ASPD 150、amotion 500ms，查 rAthena 的表才發現初心者短刀基礎值是 55，正確答案是 141 和 590ms，比原本快 200ms 一擊。

### 攻速加成的介面，給技能模組

技能的被動加成和增益的 `bonus` 字典會被 `character_data.skill_bonus` 加總後傳給 `Formulas.player_attack_delay(base_aspd, agi, dex, ranged, bonus)`，
要加攻速就在 `bonus` 放這四個鍵，數值型別是整數，不用改公式：

| 鍵 | 意義 | rAthena 對應 |
|---|---|---|
| `aspd_fixed` | 固定 ASPD 點數，乘上 AGI/200 才加進去，例如攻速藥水 +7、兩手劍修練 +7 | `status_calc_aspd(fixed=true)` |
| `aspd_percent` | 百分比，ASPD += (195 − ASPD) × p / 100，負數是懲罰 | `aspd_rate2`、`status_calc_aspd(fixed=false)` |
| `amotion_add_ms` | 直接加在 amotion 上的毫秒，負數變快 | `bonus.aspd_add`，也就是 bAspd |
| `aspd_cap` | 上限，190 到 193 之間，三轉或特定技能才用 | `max_aspd`、`max_third_aspd` |

## 3. 時間軸契約

時間都是伺服器毫秒，客戶端用 `server_clock.gd` 估的時鐘差換算。

| 時刻 | 伺服器 | 客戶端 |
|---|---|---|
| t = 0 點擊 | 收到 act.attack，下一個 tick 鎖定目標 | 送出指令；目標在攻擊距離內、不在攻擊間隔、沒在詠唱時，這一幀就面向目標並開始揮擊。命中格排在「伺服器會處理這個指令的 tick + amotion」，也就是和之後的傷害事件同一刻 |
| T0 出手 | 在 tick 邊界算好命中、暴擊、傷害，發 attack_start，下一擊排在 T0 + adelay | 收到 attack_start：如果是按下時已經先揮的那一下就接手不重播，否則收到就開始揮擊，命中格排在 amotion 之後。攻擊者面向目標是瞬間轉的 |
| T0 + amotion 命中 | 扣血、受擊硬直，發 damage | 收到就播：傷害數字在受擊者當下的畫面位置、閃白、命中停頓、擊退位移、火花、音效，全部同一幀。血條也在這一刻更新 |
| T0 + amotion 之後 | | 攻擊者收招，收招時間是 amotion × 0.25，收完回站立等下一次出手；中途移動會直接打斷收招 |
| T0 + adelay | 下一次出手 | 同上 |
| 預測失敗 | 回應 ok=false，或超過 apply tick + 250ms 沒有 attack_start | 呼叫 `cancel_attack`，動作收回站立 |

規則
- 傷害、暴擊、HP、冷卻永遠由伺服器決定，客戶端預測只改畫面，不改任何數值。
- 只有 `respawn` 這種要和內插位置對上的事件才排到內插時間播，其他戰鬥事件收到就播。
- 自己被打也一樣：怪物的 attack_start 收到就揮，damage 收到就播受擊。
- 自動攻擊設定關掉時，自己的揮擊一開始客戶端就送 act.stop 解除鎖定，這一下照樣打到，再打要再點一次。

### 命中停頓、閃白、擊退、震動

| 效果 | 數值 |
|---|---|
| 受擊方停頓 | 一般 40ms、傷害超過 HP 上限 25% 60ms、暴擊 80ms，另外不超過攻擊方 amotion 的 12% |
| 攻擊方停頓 | 受擊方的一半，一般命中最多 25ms、暴擊最多 40ms |
| 閃白 | 50ms |
| 擊退位移 | 0.24 公尺，暴擊 1.6 倍，150ms 彈回，只動顯示位置 |
| 畫面震動 | trauma 一般 0.1、暴擊 0.28、擊殺 0.25，震幅取平方，最大角度 0.25°／0.25°／0.6° |
| 傷害數字 | 0.1 秒放大到 1.2 倍，0.7 秒上飄淡出，字級和介面標題同一套 |

停頓只停當事人的動畫，不動全域時間，PVP 才不會互相干擾。

## 4. 移動契約

- 伺服器只在 tick 邊界套用移動指令。客戶端把指令排在估計的那個 tick 才套用位置，
  估法是 `server_clock.command_apply_time`：現在的伺服器時間 + 單程傳輸 − 伺服器一輪的一半，往上取到 tick 邊界。
  兩邊走同一條路線，轉向和停下都不會留下側向誤差。
- 面向和走路動作用「意圖速度」，按下的那一幀就轉向起步；位置平均晚 25ms 才動，最多一個 tick。
  RO 本身是等伺服器回傳路徑才開始走，這比 RO 快。
- 收到自己的伺服器位置時，拿「那個 tick 對應的本機時間」的預測位置來比，不是拿現在的位置。
  誤差 0.02 公尺內不理，0.12 公尺內每次修 15%，超過 0.12 公尺在 150ms 內拉回，超過 4 公尺直接換位置。
- 移動指令節流：move.dir、move.to 至少隔 50ms；從移動切到 move.stop 立刻送。最壞每秒約 22 則，低於本機 24 則和伺服器 30 則的上限。
- 攻擊鎖定時自己的位置跟著伺服器快照走，取樣時間是估計的伺服器現在，沒有內插延遲，超出最新快照的部分用速度外推最多 100ms。
- 其他實體內插延遲 60ms：本機伺服器每 50ms 一則狀態、到達抖動 10ms 內，晚到的幾毫秒靠外推補。之後接遠端伺服器要依實測抖動調大。
- 鏡頭跟隨係數從 12 改 40，幾乎鎖在角色身上，起步時角色不會先跑出畫面中心。

### 方向鍵

- 帶 Alt、Ctrl、Cmd 的按鍵是視窗快捷鍵，不算移動；放開時不管修飾鍵都算放開。
- 任何介面元件有鍵盤焦點時，方向鍵完全不動角色，點地移動不受影響。

### 4.1 詠唱中不能走，只有翻滾能打斷

2026-09-17 改。以前詠唱中按方向鍵是「打斷詠唱然後人就走掉」，
按一下方向鍵等於報銷整條詠唱條，玩家根本不知道自己取消了什麼。改成這樣：

| 詠唱中的操作 | 結果 |
|---|---|
| `move.to`、`move.dir` 往任何方向 | 整個拒絕，`last_failure` 是 `casting`。人不動，詠唱條照跑 |
| `move.stop`、零向量的 `move.dir` | 照舊接受。那是放開方向鍵，不是往前走 |
| 閃避翻滾 | 成立，並且取消詠唱，`skill_cast_cancel` 的原因是 `dodge` |
| 受傷、冰凍、暈眩 | 照舊打斷，原因分別是 `damaged` 和 `status` |
| 新的攻擊指令 | 照舊打斷，原因是 `attack` |

為什麼只有翻滾能打斷：詠唱是「站著把一段時間換成一次大傷害」的賭注，
要有一個明確的、要付代價的動作才能反悔。翻滾有 900 毫秒冷卻、120 毫秒收招、
按下去就不能出手，這個代價剛好；方向鍵沒有任何代價，不該是取消鍵。
同一顆鍵也順便解決「想閃攻擊卻只是走出去被打到」的問題：詠唱中想活命就按閃避。

沒有詠唱時間的技能不受這條規則影響。`cast_ms` 和 `fixed_cast_ms` 都是 0 的技能
還是會進 `casting`，但 `end_ms` 就等於當下，同一個時間點的下一個 `_process_moment` 就放出去，
所以判斷用的是「還有剩餘詠唱時間」`end_ms > now`，不是「有沒有在詠唱」。
怪物的詠唱是另一套 `monster_cast`，不走玩家的 `casting`，這條規則碰不到牠們。

玩家看得到的字：**一個字都沒有**。按了沒反應、詠唱條還在跑，畫面自己說明得完，
不要跳「詠唱中無法移動」這種解釋機制的訊息，見 `CLAUDE.md` 的程式規範。

客戶端要跟著擋，不然會很難用。`net_session.gd` 的 `_self_casting` 為 true 時，
方向鍵和點地移動都不送指令也不做本機預測，不然玩家會看到自己走出去再被伺服器拉回原地。
輸入端每一幀都會送一次方向，所以詠唱一結束、還按著方向鍵的下一幀就會起步，不用放開再按一次。
單機的 `battle_session.gd` 走 `battle_world.can_move`，同一條規則，測起來和連線一樣。

## 5. 角色外觀元件要提供的介面

`battle_presenter.gd` 只透過這些方法操作外觀，玩家、NPC、怪物全部是紙片 `sprite_actor.gd`，方法名稱沿用以前 3D 模型的：

| 方法 | 契約 |
|---|---|
| `play_oneshot(animation_name, duration_ms, impact_ratio, recovery_ratio)` | 播單次動作。`duration_ms` 是從現在到命中那一格的時間，通常等於 amotion，預測揮擊時會再加指令到伺服器的延遲；元件要把播放速度調成命中格剛好落在 `duration_ms`。紙片圖集有 `hit_frame` 時用它算命中比例，沒有時用 `impact_ratio`。`recovery_ratio` 大於等於 0 時命中後只留 `duration_ms × recovery_ratio` 的收招就回站立，而且中途開始移動要直接打斷 |
| `cancel_oneshot()` | 立刻結束目前的單次動作回到站立，預測揮擊被伺服器拒絕時用；不算播完，不發 `oneshot_finished` |
| `play_dodge(direction, duration_ms)` | 翻滾，整段對齊位移加收招，中途移動打不斷。圖集有 `dodge` 動作就播它，沒有就拿走路快轉，位移那一段紙片往上拱一個貼地的小跳 |
| `hitstop(ms)` | 只停這個角色的動畫 `ms` 毫秒，重疊時取較長的；停頓中顯示位置小幅抖動，判定位置不動 |
| `flash(ms, color)` | 閃色 `ms` 毫秒 |
| `knockback(direction, distance, ms)` | 顯示位置往 `direction` 推 `distance` 公尺，`ms` 內 ease-out 彈回，真實位置不動 |
| `face_direction(direction, instant)` | 面向；攻擊時 `instant` 為 true 要瞬間轉，紙片本來就是瞬間切方向 |
| `set_locomotion(speed)` | 依速度切站立或走路；正在播可打斷的單次動作而且 `speed > 0.3` 時要結束那個動作 |
| `is_playing_oneshot()`、`is_in_hitstop()` | 狀態查詢，受擊時只有沒在播單次動作才播受擊動作 |
| `play_death(name)`、`revive()` | 死亡和復活 |
| `hit_frame(animation_name)` | 紙片才有，回傳圖集標的命中格，沒有時 −1；戰鬥時間仍以伺服器 amotion 為準，這個只是把命中格對齊到那個時間 |

受擊動作用 `play_oneshot("Hit_A", 0, 1.0, 0.0)`，也就是原速播、不能被移動打斷以外的東西提早結束；紙片圖集對應 `hit` 動作。

## 6. 移動與動作手感

2026-09-16 加。使用者試玩後說「玩起來操作感很鳥，沒有流暢感」「移動 躲避 動作 感覺起來就是很死」。
第 1 到 5 節的時序在那之前已經量過也調好了，所以這一節處理的是表現和操作方式，不是網路延遲。
同一次決定把操作改成動作遊戲的方向：WASD 直接操作是主要玩法，點地移動退成輔助，並加入有無敵幀的閃避翻滾。

量測工具是 `src/dev/feel_probe.gd`，配 `--dev-feel` 在遊玩場景照固定畫格送輸入，逐幀印出動作、圖格、速度、位置。

**6.1 到 6.4 量的是 2026-09-16 那時候的 3D 模型。**2026-09-24 3D 角色整條拿掉，
量骨架步伐的 `anim_measure`、動作混合表、轉身上限、身體傾斜、借動作的 `anim_library` 跟著刪了，
紙片角色留下的是起停的顯示速度緩衝和播放速度上下限，都在 `src/world/actors/locomotion.gd`。
下面的數字留著是因為「腳在地上滑」這個結論對紙片一樣成立。

### 6.1 找到的問題

**最大的一個是腳在地上滑，而且滑得很嚴重。**
走路和跑步動作的播放速度本來是拿實際速度去除以一個寫死的「參考速度」，玩家填 1.7 和 3.4。
那兩個數字沒有來源。實際量 `body_male_hero.glb` 的動作，一輪循環左右腳各推一步，一步的前後位移是步長：

| 動作 | 長度 | 步長 | 原地播時腳在地上推的速度 |
|---|---|---|---|
| Walking_A | 1.042 秒 | 0.345 公尺 | 0.662 公尺每秒 |
| Running_A | 0.792 秒 | 0.571 公尺 | 1.441 公尺每秒 |


上面是量細節版 `body_male_hero.glb` 的。同一天換成灰白人體模型之後重量是 0.672 和 1.460，
使用者要求把角色做大做寬一點之後身高從 1.40 變 1.57，再量一次是 0.730 和 1.598。
三次量測之間程式一個常數都沒有調，因為步伐速度本來就是量出來的，不是填的。
全速跑的播放速度跟著從 2.43 倍變 2.40 倍再變 2.19 倍，腳始終跟得上。

**步伐和身高的比例才是不變量**，三套骨架分別是走路 0.886、0.890、0.890，跑步 1.926、1.949、1.949。

角色是 1.40 公尺的 Q 版比例，KayKit 骨架換成這個比例之後步伐比原作短，所以不能沿用任何原作的數字。
伺服器的玩家移動速度是 3.5 公尺每秒，跑步動作要播 3.5 ÷ 1.441 = 2.43 倍才跟得上；
但原本的參考速度是 3.4，算出來播 1.03 倍，而且還被夾在 0.7 到 1.5 之間。
**腳只走了 1.48 公尺每秒，人卻移動 3.5 公尺每秒，畫面上每一步都在冰上滑掉 58% 的距離。**
這就是「很死」最主要的來源，而且全程都在發生，不是偶爾。

其他三個：
- 轉身沒有上限。指數平滑係數 16，轉 180 度的第一幀就轉掉 42 度，量到瞬時角速度 2528 度每秒，看起來是瞬間換邊不是轉身。
- 起步和停下的動作是同一幀硬切。放開方向鍵的那一幀速度直接變 0，腳的動作立刻停住，沒有收腳。
- 所有動作換動作都用同一個 0.14 秒混合。起步該快、停下該慢、受擊該幾乎不混合，用同一個數字三邊都不對。
- 幀時間沒有問題。`--dev-perf` 在 1280×720 的萌芽草原量到穩定 60fps、每幀 17.0 到 17.2 毫秒、
  繪製 167 到 193 次、三角形約 5.4 萬、顯示記憶體 347 MB，只有進地圖那一秒是 21.7 毫秒。
  第 2 節量的 120Hz 垂直同步也仍然是穩定的 8.3 毫秒。美術長了很多但卡頓感一直都不是效能。

### 6.2 現在的規則

規則全部在 `src/world/actors/locomotion.gd`，由 `tests/test_locomotion.gd` 守住。

**步伐對速度。**播放速度是實際速度除以參考速度，夾在 0.55 到 2.60 倍。
紙片的步伐量不出來，圖集只有格數和 fps：玩家填 1.7 和 3.4，怪物用牠自己的 `move_speed`，理由見第 6.7 節。

**起步和停下。**位置仍然是按下就走、放開就停，第 4 節的移動契約沒有動。
變的是「拿來挑動作和決定播放速度的顯示速度」：
起步的那一幀直接跳到目標速度的 70%，所以走路動作在按下的同一幀就踏出去；
之後用 0.05 秒的時間常數補滿。放開時用 0.07 秒收，大約 13 幀 217 毫秒回站立。
收太慢的話角色已經站住不動、腳卻還在原地踏，那是另一種滑。

**轉身。**紙片方向直接切換不做平滑，RO 也是這樣。以前 3D 模型那個每秒 540 度的上限跟著模型刪了。

### 6.4 加新動作的規矩，不要再退回去

1. **播放速度一律照參考速度縮放，不能被上下限夾住。**新的走路圖集進來，參考速度要對上它畫的步調，

2. **圖集的動作名稱照 `docs/精靈圖規格.md`。**資料裡還寫著 `Death_A`、`1H_Melee_Attack_Stab` 這種舊名稱的地方，
   `sprite_actor.action_for` 用關鍵字對應到圖集的動作，新動作取名照圖集那一套就不用改程式。
3. **起停緩衝的數字改了要先改這一節**，測試斷言放開後 6 到 30 幀內收乾淨。

### 6.5 移動取消出手

那一下的傷害不算，下一次出手的時間只會被往後推不會提前，所以取消永遠只有代價沒有好處。
amotion、adelay 和第 3 節的時間軸一個數字都沒有動，動的只有「這段時間允不允許移動」。

|---|---|---|
| 出手後按方向鍵到真的開始移動 | 580 毫秒 | 30 毫秒，下一個 tick |

### 6.6 走路停下的鏡頭手感

2026-09-16 起鏡頭位置跟隨改成對齊 Shooter 的 `Camera2D`：
`position_smoothing_enabled`，speed 預設 5，公式是
`lerp(目前, 角色, clamp(speed * delta, 0, 1))`。

- 移動時鏡頭故意略落後，手感比較軟，不會一頓一頓。
- 停下後平滑歸到角色身上。
- 不再做移動方向預看，也不在停下時鎖死鏡頭。

旋轉、縮放、震動維持原本做法。測試見 `tests/test_battle_feel.gd`。

### 6.6.1 查過但後來改掉的做法

之前為了「停下不要往回縮」做過預看和停下鎖死，短按回朔少了但走路變頓。
使用者指定以 Shooter 為準之後改回單純的 position smoothing。
舊的煞車後仰 `LEAN_BRAKE_DEG = 0` 仍然保留，那是身體傾斜不是鏡頭。

### 6.6.2 查過但不是兇手的

排除的過程比結論有用，記下來免得下次再查一遍：

- **位置本身**：預測和伺服器停在同一個 tick、同一個位置，`tests/test_dodge.gd` 兩條測試守住。
- **動畫的根運動**：髖部相對角色節點全程 −0.000，走路混到站立不會把身體往後帶。
- **指令排到哪個 tick**：一度以為是取整取錯，因為自己搭的模型裡「先 step 再下指令」會讓
  剛好壓在邊界的指令少走一格。但真的伺服器主迴圈是**先收訊息再跑 tick**，
  所以壓在邊界上的指令會被算進那個 tick，原本的 `ceil` 是對的，這條假設不成立，已經改回去。
  記這一條是因為它示範了一件事：**量測用的模型和真的伺服器迴圈順序不一樣的話，會量出假的 bug。**

### 6.7 怪物的動畫速度對上牠自己的移動速度

2026-09-16 加。使用者反映「怪物移動不順暢動畫不順暢」。
玩家角色的步伐已經改成量出來的，紙片怪還停在填死的參考速度 1.4、播放速度夾在 0.6 到 1.6。

紙片的步伐量不出來，圖集只有格數和 fps，看不出一步跨多遠。
而且每一隻怪的走路圖集都是 8 格 12fps，但 `move_speed` 從 0.8 到 3.0 都有。
所以填一個固定的參考速度，快的怪一定會被夾住：

| 怪 | move_speed | 追擊時速度 | 改前播放 | 改後播放 |
|---|---|---|---|---|
| 空心枯樹 | 0.8 | 1.04 | 0.74 | 1.30 |
| 枯骨兵 | 1.6 | 2.08 | 1.49 | 1.30 |
| 灰蝕狼 | 2.6 | 3.38 | **1.60，夾住** | 1.30 |
| 萌芽蜂 | 3.0 | 3.90 | **1.60，夾住** | 1.30 |

灰蝕狼和萌芽蜂被夾在上限，腳只跟得上不到七成的移動距離，就是玩家角色改掉的那個滑步。

改法：**圖集是照這隻怪自己的步調畫的，所以牠自己的 `move_speed` 就是參考速度。**
閒晃 0.6 倍速播 0.6 倍、追擊 1.3 倍播 1.3 倍、回家 1.6 倍播 1.6 倍，
一隻怪一個標準，不用魔術數字，也不會被夾。播放上下限用 `Locomotion` 的那一組。

同時 `sprite_actor` 也接上 `Locomotion.ease_speed`：起步在同一幀就切到走路，
停下留一小段收腳，不再硬切。怪物被打停頓和出手時速度歸零那一下也跟著變柔。

### 6.8 命中的畫面震動

2026-09-16 加。使用者反映「戰鬥打擊感弱」。逐幀看下來火花、閃白、擊退、傷害數字都有在做，
**唯一完全沒有作用的是畫面震動**，而且是兩個錯疊在一起：

1. **震幅小到看不見。**一般命中 trauma 0.1，取平方變 0.01，乘上最大角度 0.25 度等於轉 0.0025 度。
   FOV 15 度配 720 像素是每度 48 像素，所以畫面只動了 **0.12 像素**。暴擊也才 0.94 像素。
   震幅取平方是 Eiserloh 的正確做法，但基底 trauma 太小，平方之後就歸零了。
2. **根本不會抖。**`_shake_time` 每秒前進 38，`FastNoiseLite` 的 frequency 是預設的 0.01，
   實測每秒只換邊 0.5 次，也就是一個波長 2.6 秒；但震動本身只存在 0.2 秒。
   那不是抖動，是一次緩慢的偏移。

改後，FOV 15 度配 720 像素，四十種雜訊相位取樣：

| | 改前 | 改後 |
|---|---|---|
| 一般命中畫面位移 | 0.12 像素 | 平均 2.2、最壞 4.0 像素 |
| 暴擊畫面位移 | 0.94 像素 | 平均 7.6、最壞 12.3 像素 |
| 每秒抖幾下 | 0.5 | 11.6 |
| 一次震動持續 | 0.22 秒 | 0.13 秒，衰減從 1.6 改 2.6 |

雜訊的輸出實測是正負 0.65 不是正負 1，所以多了一個正規化，`SHAKE_MAX_DEG` 寫的角度才有意義。
`tests/test_battle_feel.gd` 守住震動看得見、暴擊明顯比一般大、以及一次震動抖的次數落在 3 到 20 之間。

**沒有動的：**傷害數字的字級是 2026-09-15 使用者嫌太大才調小的，不能調回去；
火花、閃白、擊退逐幀看都有作用，沒有理由一起加。

**音效那一邊查出來的原因不是品味，是 3D 衰減模型在聽者附近放大又夾在 +3 dB，
所以強擊和暴擊出來的波形一模一樣而且破音。**修法在音效那邊，但留下一條跨模組的規則：

> `battle_presenter.damage()` 裡從命中音效到火花這一段必須是連續的，
> 中間不能插入任何 `await`、`create_tween`、`create_timer` 或 deferred 呼叫。
> 聲音、凍結、閃白、火花差幾幀出現，打擊感就會變軟。
> 聲音的級別也用和 `hitstop_ms()` 同樣的 `crit` 和 `heavy` 兩個旗標。

這條規則本來只存在對話裡，很容易在重構時被改壞，所以 `tests/test_battle_feel.gd` 直接讀原始碼守住：
檢查四件事的順序，以及那一段裡不准出現會跨幀的呼叫。

### 6.9 繞過障礙時預測會偏掉，已修，改的是資料不是程式

2026-09-17。碰撞那邊修好「目標落在不可行走區就整個丟掉指令」之後，剩下一個小的：
伺服器每 tick 走一步、客戶端每幀走一步，同一段移動切成不同大小的步，繞過障礙時會走出不同路線。

量下來的關鍵不是大小，是形狀：

| 障礙 | 步長差距 | 超過 0.12 的修正門檻 |
|---|---|---|
| 直牆、方形 | 0.000 到 0.005 | 否 |
| 圓形 半徑 0.55 到 3.4 | 0.105 到 **0.225** | **是，整個範圍都超過** |

**只有法線會轉的形狀會偏。**方形每一個面的法線固定，沿邊滑動和步長無關，切幾步都一樣；
圓形的法線一路在轉，大步走的是弦、小步貼的是弧，必然分岔。

原本的結論是「要改客戶端預測，讓它照 tick 邊界推進」，那是個大改動：
`Prediction.step` 要改成固定步長，畫面會變成每秒 20 格的階梯，還要再加一層算繪內插，
那一層會動到第 2 節和第 4 節量過的輸入延遲，而且 `MODE_DODGE`、攻擊鎖定跟隨、
停下排程和十幾條測試都壓在 `step` 上面。

**但既然方形免疫，便宜的路線是改資料不是改程式。**地圖上 88 個圓形不可行走區
全部換成等面積的方形之後：路燈柱 0.0004、城鎮樹 0.0087、最壞的崗哨塔 0.0133，
全部遠在門檻之內，而且方形的碰撞測試比圓形還便宜 13%，等於不花成本。
碰撞那邊也試過在 `move()` 裡改成沿著弧滑而不是沿著切線弦滑，量下來 0.177 到 0.181 沒有改善，
反向證實了偏差來自呼叫端每一步重新瞄準，不是 `move()` 內部能解決的。

所以客戶端預測維持照畫面更新推進，不改。

**現在整個遊戲的碰撞都壓在「方形的步長無關性」上**，`tests/test_prediction_steps.gd` 守住它，
而且把面和角分開量：

| | 實測最大 | 說明 |
|---|---|---|
| 滑過面 | 0.0045 | 法線固定，兩邊幾乎完全一樣 |
| 擦過角 | 0.048 | 角落的法線是跳的，這裡還是會分岔，而且跟著邊長長 |

擦角那一項在 6 公尺的方形上是 0.048，還在門檻內；之後如果出現邊長遠大於 6 公尺的方形要重新量。
「出貨資料裡沒有圓形」由碰撞那邊的 `test_shipped_maps_have_no_circular_blockers` 和
`test_footprint_table_uses_squares_not_circles` 守，不重複。

另外留了一條 `test_修正門檻不能被調大來蓋住問題`：
把 `CORRECTION_DISTANCE` 調大看起來會讓這類問題消失，實際上只是讓該修正的誤差不再被修正。
指令的 tick 估錯一格會產生 0.175 公尺的側向誤差，門檻一定要留在那之下。

## 7. 閃避翻滾

2026-09-16 加。使用者選了動作遊戲的方向，閃避是「你為什麼活下來」的那個機制。
規則和數字在 `src/core/dodge.gd`，常數在 `data/balance.json` 的 dodge 區，指令契約在 `docs/伺服器架構.md` 第 3 節。
**伺服器是唯一判斷有沒有無敵的地方**，客戶端只送方向。

### 7.1 時間窗

一次閃避分三段，時間從按下的那個 tick 起算：

| 段 | 時間 | 內容 |
|---|---|---|
| 起步 | 0 到 40 毫秒 | 還打得到。這一小段是留給對手的公平空間，沒有它閃避就是無敵鍵 |
| 無敵 | 40 到 240 毫秒 | 這段時間內結算的攻擊全部算閃掉，不扣血、不硬直、也不擊退 |
| 位移 | 0 到 300 毫秒 | 往指定方向 2.4 公尺，速度 8.0 公尺每秒，是跑步的 2.3 倍；撞到不可行走區沿邊滑 |
| 收招 | 300 到 420 毫秒 | 已經不無敵也還不能出手、不能再閃、不能自己走。這是閃避的代價 |
| 冷卻 | 900 毫秒 | 從按下那一刻起算，冷卻跟著角色換地圖和斷線重登 |

無敵窗 200 毫秒刻意比位移 300 毫秒短，也刻意遠短於冷卻 900 毫秒：
怪物的預警是 900 到 1600 毫秒，看到預警再按來得及；但無敵不能蓋滿整段位移，
不然連續閃避就變成無敵位移，看預警就沒有意義了。實測連灌指令時無敵時間占比是 22%。

### 7.2 取消規則

- **出手中可以閃。**還沒結算的那一下會被丟掉：想用閃避躲掉自己的破綻，就得放棄那一擊，不能又打到又閃掉。
  已經結算過的傷害不受影響。下一次普攻的時間只會被往後推，不會提前，所以閃避不會變成加速輸出的手段。
- **詠唱中閃避會打斷詠唱**，取消原因是 `dodge`。翻滾是唯一能主動打斷詠唱的操作，
  移動指令在詠唱中會被整個拒絕，見第 4.1 節。坐著休息閃避會站起來。
- **冰凍、暈眩、被絆住時閃不動**，分別回 disabled 和 rooted。死亡回 dead。
- 閃避會解除攻擊鎖定，和玩家自己下移動指令一樣。

### 7.3 操作

- 電腦：空白鍵。往目前按住的方向閃，沒按方向就往角色面向的方向閃。按住不會連續翻滾，只認按下的那一下。
- 手機：右下角一顆 56 像素的閃避鈕，排在技能弧線外側的斜上方，往搖桿目前推的方向閃。
  不能放攻擊鈕正上方，那一格是技能弧線最上面那一顆，第一版就疊在一起，截圖才看出來。
- 紙片角色的翻滾是 `sprite_actor.play_dodge`：圖集有 `dodge` 動作就播它，還沒畫就拿走路那段快轉，
  位移那一段紙片往上拱一個身高 6% 的貼地小跳，收招那段貼回地面。紙片只有八個方向，不分前後左右滾。
  **動作不能自己帶位移**：翻滾距離是伺服器決定的、客戶端已經照它推位置了，動作再帶位移畫面就會走兩次。
  **鎖定目標時角色維持面向敵人**，沒有鎖定時才整個人朝翻滾方向。
  以前 3D 模型用四個方向的 `Dodge_*` 動作，來源是 `art_pipeline/characters_v3/dodge_anim.py`，那支還留在紙偶骨架的動作庫裡。
- 整段動作對齊 420 毫秒的位移加收招，翻完站起來的那一刻剛好恢復操作。

### 7.4 預測

閃避和移動指令走同一套預測：動作在按下的那一幀就播，位置照 `server_clock.command_apply_time`
排在伺服器會處理這個指令的那個 tick 才開始滾，兩邊走同一條路線，翻滾結束不需要修正。
`prediction.gd` 的 `MODE_DODGE` 和伺服器的 `_dodge_advance` 是同一條規則：固定方向、固定速度、走固定時間。
伺服器拒絕時客戶端停下預測並把動作收回站立，位置交給一般的修正拉回去。
客戶端自己也記一份冷卻，只用來擋住明顯按太快的按鍵，真正說了算的永遠是伺服器回來的 `dodge_start`。

## 6. 還沒做和要注意的

- 位置起步平均晚 25ms 是刻意的取捨：立刻動的話伺服器會落後最多一個 tick，轉向和放開都會留下最多 0.175 公尺的側向誤差，只能用修正慢慢滑回去。要改成立刻動只要把 `net_session._send_moves` 的 `apply_ms` 改成 `now`。
- tick 估錯一個時，側向誤差 0.175 公尺在移動中會在 150ms 內拉回，看得到一小下；實測約十次轉向出現一次以內。**已經停著時改成一次對齊**，短按不會再被平滑拉回讀成往回退。
- 從移動切到 `move.stop` 會立刻送出，不再等 50ms，短按才不會多走半步。
- 攻速公式和 RO 不同，見第 2 節。
- 紙片角色的圖集還沒有 `dodge` 動作，翻滾先拿走路快轉加小跳頂著，要畫一段真的翻滾。
- 紙片角色的步伐沒有量測，仍然靠圖集張數和填進去的參考速度，怪物大多走這條路；正式怪物美術進來時要一起處理。
- 鏡頭距離 2026-09-18 定成預設 52 公尺、範圍 24 到 52，角色 1.57 公尺；
  52 公尺時角色貼圖縮成 0.82 倍，1080p 上約 124 像素高，還看得出閃避。
  玩家可以自己滾到 42.73 看一比一的角色。
- 遠端伺服器上線後要重新量抖動再定內插延遲。
