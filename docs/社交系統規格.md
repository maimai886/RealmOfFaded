## 2. 交易

### 2.1 狀態機

一場交易只有四個狀態，紀錄只在記憶體，永遠不存檔。

```
none ──trade.request──▶ pending ──trade.accept──▶ open ──兩邊都確認──▶ done ──▶ none
                           │                        │
                           │                        ├─ trade.offer / trade.gold ─▶ open，版本加一，兩邊確認清掉
                           │                        ├─ trade.confirm ─▶ open，自己標成已確認
                           │                        └─ 中斷 ─▶ none
                           ├─ trade.refuse ─▶ none
                           └─ 30 秒沒回應、被邀請的人斷線 ─▶ none
```

- `pending` 只記在被邀請的人身上，`{from_id, from_name, until_ms}`，30 秒沒回應就失效
- `open` 兩邊各有一份擺出來的東西 `{items: {道具 id: 數量}, gold, confirmed}`
- 擺上去的道具、指名的裝備和金幣當場押住，交易結束前不能賣、丟、用、穿、精煉、存倉庫、花掉、再擺一次；
  東西還留在背包裡，只是押著，存檔永遠是完整的背包。做法在 `docs/伺服器架構.md` 第 3.0 節
- 客戶端收到的背包已經扣掉押住的數量，擺出去的東西在背包裡看不到，只在交易欄看得到
- 任何一方改動擺出來的東西，交易的 `version` 加一，兩邊的 `confirmed` 一起清掉
- `trade.confirm` 一定要帶目前看到的 `version`，帶舊的回 `stale_offer`
- 兩邊都 `confirmed` 的那一瞬間就檢查並交換，沒有第三個等待狀態
- `done` 只是換完之後的瞬間，緊接著就回到 `none`，客戶端收到的是 `stage: none` 加 `reason: done`

### 2.2 中斷

下面任何一項成立，交易在伺服器的下一輪就取消，東西原封不動留在原本的人身上，押住全數放開：

| 中斷原因 | 推送的 reason |
|---|---|
| 任何一方斷線、離開地圖、角色被刪掉 | `partner_left` |
| 任何一方換地圖、走出 5 公尺、兩個人不在同一張地圖 | `too_far` |
| 任何一方倒下 | `dead` |
| 任何一方打開商店或倉庫 | `trade_busy` |
| 任何一方進入戰鬥，也就是 10 秒內打過人或被打、身上有怪物鎖定、自己鎖著目標 | `in_combat` |
| 任何一方按取消或關掉交易視窗 | 按的人 `cancelled`，另一邊 `partner_cancelled` |

### 2.3 交換

兩邊都確認之後，順序是：

1. 重新跑一次第 2.2 節的中斷檢查，不過關就取消
2. 兩邊擺出來的東西還在不在背包和身上，數量對不對，金幣夠不夠
3. 在背包的**複本**上試做：自己擺出去的先拿掉，再收下對方的，檢查格子數、疊放上限、負重
4. 金幣算完之後不能小於 0，也不能超過 `CharacterData.MAX_GOLD`
5. 任何一項不過就整筆不做，兩邊的確認清掉，交易**不取消**，玩家可以調整之後再確認一次
   放不下的那一邊看到 `overweight` 或 `inventory_full`，另一邊看到 `partner_overweight` 或 `partner_inventory_full`
6. 全部通過才寫 `trade.done` 稽核，接著改背包、用 `game_server.change_gold` 改金幣，最後兩邊立即存檔

穿在身上的裝備不在背包裡，所以第 2 步就擋掉了「交易身上穿著的東西」，不用另外寫規則。
道具資料的 `no_trade` 為 true 時擺不出來，寫法和 `no_sell` 一樣；目前的資料沒有任何一筆是 true。

## 3. 好友

### 3.1 資料

好友和封鎖名單存在**帳號紀錄**的 `social` 欄位，和帳號倉庫一樣有 HMAC 簽章和版本日誌，改檔會被隔離。

```
{
  "friends": [{"id": 角色 id, "name": 角色名稱, "added_at": unix 秒}],
  "blocked": ["小寫角色名稱"]
}
```

- 好友記角色 id，對方上線時名字跟著角色紀錄更新；角色被刪掉之後那一筆查不到人，永遠顯示離線
- 封鎖記小寫名稱，對方不在線上也封鎖得了，和 RO 的無視名單一樣
- 進地圖時讀進記憶體，在線期間都用同一份，有變動就立刻寫回帳號紀錄
- 讀回來的內容一律經過 `Social.sanitize`：壞掉的項目丟掉、重複的只留第一筆、超過上限的截掉
- 帳號紀錄整份讀不回來時給一份空名單，角色還是進得了地圖，只是這次連線用不了好友功能

### 3.2 指令

| 指令 | 檢查 |
|---|---|
| `friend.add` | 不能加自己、對方在線上且同一台伺服器、還不是好友、兩邊的名單都沒滿、對方沒有還沒回應的邀請、同一個人連續邀請至少隔 1 秒 |
| `friend.accept` | 邀請存在、沒過期、邀請人還在線上；通過後**兩邊互加**並各自寫回帳號紀錄 |
| `friend.refuse` | 邀請存在；會通知邀請人 |
| `friend.remove` | 對方在自己的名單裡；**只刪自己這一份**，對方的名單不動 |
| `block.add` | 名稱合法、不是自己、還沒封鎖過、名單沒滿 |
| `block.remove` | 名稱在封鎖名單裡 |

失敗原因：`target_self`、`target_offline`、`already_friend`、`not_friend`、`friends_full`、
`target_friends_full`、`already_blocked`、`not_blocked`、`blocked_full`、`block_self`、
`no_friend_request`、`friend_request_expired`、`already_requested`、`name_invalid`、`rate_limited`、`server_error`。

### 3.3 推送

`friend.list` 帶整份名單，每一筆是 `{id, name, online, map, map_name, level, job_id}`，另外帶
`max_friends` 和 `max_blocked` 讓介面顯示上限。送出時機：

- 自己進地圖、加好友、刪好友、封鎖、解除封鎖
- 名單上的人上線、下線、換地圖時，推給有把他加在名單裡而且正在線上的人

線上人數不多，上下線時直接掃一遍線上玩家；人多之後要改成角色 id 對應好友的反向索引，見第 7 節。
後進地圖的人一進來就看得到已經在線上的好友，測試是 `test_friend_list_shows_who_is_already_online`。

## 4. 密語與封鎖

- `chat.whisper {to, text}`，文字長度和一般聊天一樣 1～120 字，字元檢查走協定層的共用規則
- 同一台伺服器上線的角色才收得到，對方不在線上回 `whisper_offline`，密語自己回 `whisper_self`
- 送出的人一定會收到一則自己說的話的回顯，`mine` 為 true，介面顯示成「對 X 說」
- 對方把自己封鎖時：**照樣回成功、照樣回顯**，但訊息不會送到對方那裡
  這是故意的，騷擾者看不出自己被封鎖，不然他會換角色再來一次
- 封鎖也擋掉交易邀請和好友邀請，而且回的原因和「對方不在線上」一模一樣，封鎖了誰不會外流
- 密語走 `chat.` 開頭，和一般聊天共用每秒 2 則的桶，洗密語和洗聊天一樣擋

## 7. 仍存在的風險

- **交換之後的兩筆存檔不是同一個交易**：`apply_swap` 在記憶體裡一次換完，接著先存 A 再存 B。
  如果剛好在兩筆寫入之間當機，重開後可能一邊已經寫進去、一邊還是舊的，那就是複製或消失。
  現在的緩解是**稽核 `trade.done` 在改動之前就寫進 append-only 日誌**，兩邊的道具和金幣都記著，事後查得出來也補得回來。
  真正的解法是資料庫層的交易，換成 SQLite 或 PostgreSQL 時一起補，見 `docs/伺服器架構.md` 第 5 節。
- **好友上下線通知靠掃線上玩家**：每次有人上下線或換地圖就掃一遍線上名單。
  幾百人以內沒問題，再多要改成反向索引。
- **封鎖只擋密語、交易邀請和好友邀請**：一般聊天、隊伍頻道和畫面上的名字還是看得到，和 RO 一樣。
- **跨伺服器**：好友、密語、交易都只在同一台伺服器上找人。

## 8. 和 rAthena 不同的地方

| 項目 | rAthena | 本作 | 理由 |
|---|---|---|---|
| 交易距離 | 2 格，換算約 1 公尺 | 5 公尺 | 本作的角色體型和鏡頭距離都比 RO 大，1 公尺等於貼在一起；5 公尺在畫面上的感覺和 RO 站隔壁一樣 |
| 確認流程 | 兩階段，先 ok 鎖定再 trade 成交 | 一階段加版本號 | 兩階段是為了擋「對方鎖定後偷改內容」；版本號直接讓舊的確認失效，少一個狀態、少一種卡住的情況，擋的東西一樣 |
| 交易中被打 | 只在部分情況中斷 | 一律取消 | 交易視窗蓋住畫面時打不了架，讓玩家用交易視窗擋傷害等於多一個漏洞 |
| 基本技能 1 級才能交易 | `basic_skill_check` 要 NV_BASIC 1 級 | 不擋 | 使用者要求「原版 RO 那樣啥都不教你、不限制你」；新角色技能 0 級，擋了等於整個功能開局不能用。倉庫的 6 級限制是 RO 玩家本來就知道的規則，留著 |
| 交易格數超過時 | 客戶端自己擋 | 伺服器回 `trade_slots_full` | 客戶端的檢查一律不算數 |
| 擺出去的東西 | `trade_tradeadditem` 只記格子，交易中靠 `state.trading` 擋丟道具和開商店倉庫，成交時 `impossible_trade_check` 抓多擺的 | 擺上去的數量和那幾件押住，所有扣道具和花錢的路徑都扣不到；成交時照樣重新比對 | rAthena 靠一條條入口各自擋，漏一個就是複製；押住放在背包本身，新加的扣道具路徑自動跟著擋 |
| 被無視時的密語 | 靜靜丟掉 | 靜靜丟掉，而且照樣回顯給送出的人 | 回顯讓送出的人完全看不出差別，比只是丟掉更難試探 |
| 好友是角色的 | 每個角色一份 | 每個帳號一份 | 使用者要求存在帳號上；同一個帳號換角色不用重加一次 |
| 好友上線通知 | 送一則單獨的上線訊息 | 重推整份名單 | 名單最多 40 筆，整份推比較單純，也不會漏掉換地圖 |

## 9. 公會：這一次刻意沒有做

公會需要的東西是：建立、邀請、退出、踢人、職位與權限、公會頻道、公會存檔、公會經驗與等級、
公會技能、公會標誌、公會倉庫、公會對戰。只做「名字加成員加隊長加一個頻道」等於再做一次隊伍，
放進遊戲之後玩家看到的是一個什麼都不能做的空殼，也就是 `CLAUDE.md` 說的籠統半成品。
公會要自己一輪，照隊伍的做法先寫 `docs/公會規格.md`，再決定和隊伍、倉庫、地圖的關係。
目前 `chat.say` 的 `guild` 頻道在協定裡還是關著的，`player_commands.OPEN_CHAT_CHANNELS` 沒有它。
