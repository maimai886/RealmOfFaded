# 程式規範

2026-09-27 製作人訂，所有崗位照這份寫。使用者：「整體代碼風格要簡單好讀 所以目標都以最少代碼且能達到目標為準」。

## 1. 目標

**用最少的程式碼做到目標，而且一眼看得懂。** 兩個寫法都做得到時，挑短的那個；短的比較難懂時，挑好懂的那個。

## 2. 註解

使用者：「注釋精簡不超過一行表達重點別寫廢話」。

- 一則註解最多一行
- 只寫程式本身看不出來的事：為什麼這樣做、數字的來源、會踩到的坑
- 不寫程式在做什麼，名字取好就不用註解
- 檔案開頭一行講這個檔做什麼；函式名字講得清楚就不寫
- 不寫日期、改動歷史、誰改的，那些在 git 裡
- 繁體中文白話，不用括號補充

```rust
// 好：只寫看不出來的
// 舊 JSON 的整數常寫成 1.0
fn lenient_i64(v: &Value) -> Option<i64>

// 不好：重複程式在做什麼
// 這個函式把 JSON 的值轉成整數，如果是浮點數而且沒有小數就轉，否則回傳 None
```

## 3. 寫法

- **只寫現在的里程碑要的**。不為以後可能要的功能留介面、留參數、留設定
- **重複三次才抽出來**，兩次照抄比多一層抽象好讀
- **先找標準庫和成熟套件**，有的就不自己寫；加套件前確認它還有人維護
- **用不到的程式當場刪**，不留註解掉的程式，不留「以後可能用到」
- **一個函式做一件事**，超過一個畫面長就看看能不能拆；拆不好就不拆
- **名字寫完整的英文單字**，不用縮寫，`damage` 不寫 `dmg`
- **錯誤只在邊界處理**：封包、檔案、玩家輸入要檢查；程式內部互相呼叫不重複檢查

## 4. Rust

- 用型別表達規則：封包和資料用 serde 的 derive 自動驗證，不手寫欄位檢查；有限的種類用 enum，不用字串
- 錯誤用 Result 往上傳；伺服器不准因為一個玩家的封包 panic
- 不寫 unsafe，gdext 規定的除外；不寫巨集，除非省下的程式碼很明顯
- 泛型和 trait 只在真的有兩種以上實作時才用
- `cargo fmt` 排版，`cargo clippy` 不留警告
- 只有 `rof-gdext` 依賴 godot，其他 crate 不准

## 5. GDScript，只有介面

- 介面向擴充拿資料、把玩家按的東西交給擴充，不算數值、不判規則、不碰世界裡的節點
- 用 `preload` 常數引用腳本，不用 `class_name`
- 字級、顏色、樣式只用 `src/ui/ui_theme.gd`
- 從舊專案搬介面時，順手把用不到的分支和重複的程式刪掉，不照搬

## 6. 行數預算

每個里程碑結束時回報行數，空行和註解不算，用 `tokei` 或同樣算法：

| 里程碑 | Rust 加介面的總行數上限 |
|---|---|
| M1 走路 | 6,000 |
| M2 打一隻 | 10,000 |
| M3 初心者 | 20,000 |

舊專案做到同樣範圍約 3 萬行。超過預算不是不准，但要在回報裡講清楚多出來的是什麼、為什麼省不掉。

## 7. 交付前自己刪一輪

交出去之前把自己的改動從頭讀一遍，問三件事：

- 這一行刪掉，功能會壞嗎？不會就刪
- 這則註解刪掉，下一個人會看不懂嗎？不會就刪
- 這段有沒有更短的寫法？有就改
