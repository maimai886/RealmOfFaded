# 程式規範

2026-09-27 製作人訂，所有崗位照這份寫。使用者：「整體代碼風格要簡單好讀 所以目標都以最少代碼且能達到目標為準」「注釋精簡不超過一行表達重點別寫廢話」。

## 1. 寫法

- 用最少的程式碼做到目標；兩種寫法都做得到時挑短的，短的比較難懂時挑好懂的
- 只寫現在的里程碑要的，不為以後留介面、參數、設定；用不到的程式當場刪，不留註解掉的程式
- 重複三次才抽出來；先找標準庫和還有人維護的成熟套件
- 一個函式做一件事；名字寫完整的英文單字，`damage` 不寫 `dmg`
- 錯誤只在邊界檢查：封包、檔案、玩家輸入；程式內部互相呼叫不重複檢查

## 2. Rust

- 封包和資料用 serde derive 驗證，不手寫欄位檢查；有限的種類用 enum 不用字串
- 錯誤用 Result 往上傳，伺服器不准因為一個玩家的封包 panic
- 不寫 unsafe，gdext 規定的除外；巨集、泛型、trait 只在明顯省程式或真的有兩種以上實作時才用
- `cargo fmt` 排版，`cargo clippy` 不留警告；只有 `rof-gdext` 依賴 godot

## 3. GDScript，只有介面

- 向擴充拿資料、把玩家按的東西交給擴充，不算數值、不判規則、不碰世界裡的節點
- 用 `preload` 常數引用腳本，不用 `class_name`；字級、顏色、樣式只用 `src/ui/ui_theme.gd`
- 從舊專案搬介面時，順手刪掉用不到的分支和重複的程式

## 4. 註解

最多一行，只寫看不出來的事：為什麼、數字的來源、會踩的坑。不寫程式在做什麼、日期、改動歷史。檔案開頭一行講這個檔做什麼。

## 5. 交付前

把自己的改動從頭讀一遍：刪了功能不會壞的行就刪，刪了下一個人照樣看得懂的註解就刪，有更短的寫法就改。測試照 `Rust重構規劃.md` 第 6 節。

## 6. 行數預算

每個里程碑結束時回報行數，空行和註解不算，用 `tokei` 或同樣算法，測試也算：

| 里程碑 | Rust 加介面的總行數上限 |
|---|---|
| M1 走路 | 6,000 |
| M2 打一隻 | 10,000 |
| M3 初心者 | 20,000 |

舊專案做到同樣範圍約 3 萬行。超過預算不是不准，但要在回報裡講清楚多出來的是什麼、為什麼省不掉。
